### claude-01

- **reviewer**: claude
- **severity**: HIGH
- **kind**: point
- **domain**: security
- **title**: Одиночный `\r` в подставляемом значении не отвергается — обход защиты «команда вставляется, но не исполняется»
- **mechanism**: `render` отвергает значение по признаку `value.includes('\n')`. Одиночный `\r` (CR, U+000D) этой проверкой не ловится: тест покрывает только `\r\n`, где `\n` присутствует. В терминале VS Code текст уходит в pty; в каноническом режиме CR — это и есть нажатие Enter (`icrnl`), поэтому имя каталога, содержащее `\r`, исполняет строку до него независимо от `execute: false`. POSIX/PowerShell-квотирование здесь не помогает: CR внутри `'...'` литерален для парсера шелла, но перевод строки делает не шелл, а строчная дисциплина терминала.
- **trigger**: воспроизводится в нормальной работе — достаточно каталога с `\r` в имени в склонированном чужом репозитории (сценарий, прямо названный моделью угроз 00-overview.md: «данные с диска»)
- **in_scope**: да
- **anchor**: `packages/projects-tree/src/projects/actions/render.ts:78-84`
- **evidence**:
  ```ts
  const value = lookupVariable(variableName, node);
  if (value.includes('\n')) {
    throw new RenderError(
      'newlineInValue',
  ```
- **verification**: confirmed
- **verification_note**: проверка по коду однозначна (`includes('\n')` ложно для строки `'a\rb'`); в `render.test.ts` есть кейс `'/tmp/a\r\nb'` и нет кейса с одиночным `\r`. Контракт плана — «Перевод строки в значении отвергается всегда» (00-overview.md, «Модель угроз») — на CR не выполняется.
- **fix_direction**: расширить признак отказа до любого символа-разрыва строки, значимого для терминала и pty (как минимум CR, плюс решение по U+2028/U+2029 и `\v`/`\f` — обосновать явно), и завести отдельный тест на одиночный CR, а не только на CRLF.

### claude-02

- **reviewer**: claude
- **severity**: HIGH
- **kind**: point
- **domain**: tests
- **title**: Тесты квотирования пропускают неполное экранирование одиночной кавычки (round-trip тавтологичен)
- **mechanism**: Матричный тест проверяет `unquote(quoteForShell(v)) === v`, где `unquote` для POSIX снимает внешние кавычки и делает `replaceAll("'\\''", "'")`. Такой round-trip зелёный и для реализации, которая экранирует кавычку неполно, и даже для той, которая не экранирует её вовсе (`slice(1,-1)` возвращает исходную подстроку). Единственная реальная проверка — три штучных ассерта на `"it's"` (по одной кавычке в значении), поэтому ни один кейс в наборе не имеет двух одиночных кавычек. Проверено исполнением: замена `value.replaceAll("'", ...)` на `value.replace("'", ...)` в `quoteForPosixShell` (экранируется только первая кавычка) оставляет все 64 теста в `actions/` зелёными. Дефект при этом эксплуатируем: для значения `A'q'; id; '#` вывод `'A'\''q'; id; '#'` парсится шеллом как слово, затем `;`, затем `id` — состояние кавычек десинхронизируется и метасимволы значения выходят из-под квотирования.
- **trigger**: воспроизводится в нормальной работе — тест-набор не защищает инвариант, ломка реализации не краснеет
- **in_scope**: да
- **anchor**: `packages/projects-tree/src/projects/actions/quoting.test.ts:18-24`
- **evidence**:
  ```ts
  expect(quoted.startsWith("'")).toBe(true);
  expect(quoted.endsWith("'")).toBe(true);
  return quoted.slice(1, -1).replaceAll(String.raw`'\''`, "'");
  ```
- **verification**: confirmed
- **verification_note**: ломка выполнена и откачена (`git status` чистый): `pnpm exec vitest run packages/projects-tree/src/projects/actions` → 64 passed при неполном экранировании
- **fix_direction**: перестать полагаться на round-trip как на основной инвариант и добавить проверки, устойчивые к неполному экранированию: значения с несколькими одиночными кавычками (в том числе подряд и по краям) и структурный ассерт на то, что в квотированной форме не остаётся ни одной «свободной» кавычки, способной переключить состояние квотирования. Отдельно — зафиксировать явные ожидаемые строки для каждого шелла, а не только для `"it's"`.

### claude-03

- **reviewer**: claude
- **severity**: HIGH
- **kind**: point
- **domain**: security
- **title**: Экран сложности регулярок пропускает классический экспоненциальный бэктрекинг на перекрывающейся альтернации
- **mechanism**: `checkRegexComplexity` ищет только два признака: обратные ссылки и квантификатор на группе, внутри которой уже есть квантификатор. Семейство «перекрывающаяся альтернация под квантификатором» (`(a|a)*`, `(a|ab)*`, `(?:a|a)+`) внутренних квантификаторов не содержит и экран проходит, хотя даёт ровно тот экспоненциальный бэктрекинг, от которого экран поставлен. Проверено исполнением: `^(?:a|a)*$` признан `safe: true`, а `new RegExp('^(a|a)*$').test('a'.repeat(30) + 'b')` занял **61 119 мс** в том же прогоне (тест упал по таймауту vitest, 5000 мс). Прерывать синхронный `RegExp` в Node нечем (это прямо сказано в 00-overview.md), поэтому одно правило `nameMatches` с таким шаблоном подвешивает extension host на имени каталога длиной в десятки символов. Второй пропуск того же экрана — полиномиальный бэктрекинг без вложенности (`\w+\s?\w+\s?\w+\s?$`, тоже `safe: true`).
- **trigger**: воспроизводится в нормальной работе — правило пишет пользователь в файле правил; после 02-B такой шаблон проходит валидацию как безопасный
- **in_scope**: да
- **anchor**: `packages/projects-tree/src/projects/classification/regex-safety.ts:33-46`
- **evidence**:
  ```ts
  if (hasNestedQuantifier(pattern)) {
    return { safe: false, reason: 'a quantifier applied to a group that already contains one ...' };
  }
  return { safe: true };
  ```
- **verification**: confirmed
- **verification_note**: временный probe-тест в пакете (создан, прогнан, удалён; `git status` чистый): `checkRegexComplexity` вернул `safe: true` для `(a|a)+$`, `(a|ab)*c`, `^(?:a|a)*$`, `\w+\s?\w+\s?\w+\s?$`; замер времени 61 119 мс на входе длиной 31 символ
- **fix_direction**: расширить экран как минимум на квантификатор над группой с альтернацией, ветви которой могут совпасть по первому символу (перекрытие альтернатив), и назвать в комментарии остаточный класс (полиномиальный бэктрекинг) явно. Альтернатива, снимающая весь класс сразу и уже названная в плане как условие пересмотра, — линейный движок вместо эвристики; тогда эвристику надо не расширять, а убирать. Отдельно: тест на экран должен содержать кейсы, которые он НЕ ловит, с зафиксированным ожиданием, иначе следующая правка снова оставит их незамеченными.

### claude-04

- **reviewer**: claude
- **severity**: HIGH
- **kind**: point
- **domain**: security
- **title**: `pathMatches` с `**` в середине глоба теряет границу сегмента и совпадает лишнее
- **mechanism**: В `globToRegExp` фрагмент для `**` в середине — `(?:.*/)?`, и при этом слэш между предыдущим литеральным сегментом и `**` не выводится (ветка `part === null` уходит в `continue` до вставки `/`, а следующий литеральный сегмент видит `parts[index-1] === null` и тоже `/` не ставит). В результате глоб `a/**/b` компилируется в `^a(?:.*/)?b$`: он совпадает не только с `a/b` и `a/x/b`, но и с `ab`, `aQ/b`, `aQ/R/b`. Первый сегмент перестаёт быть точным сегментом — он становится префиксом. Для правила это тихая эскалация области действия: `pathMatches: 'work/**/secret'` начинает срабатывать на `workspace/secret`, а `skip`/`project`-вердикт применяется к узлам, которых автор правила не имел в виду.
- **trigger**: воспроизводится в нормальной работе — достаточно любого правила с `**` в середине глоба
- **in_scope**: да
- **anchor**: `packages/projects-tree/src/projects/classification/condition.ts:139-157`
- **evidence**:
  ```ts
  } else {
    pattern += '(?:.*/)?';
  }
  continue;
  ```
- **verification**: confirmed
- **verification_note**: временный probe-тест (создан, прогнан, удалён): `compileCondition({kind:'pathMatches', glob:'a/**/b'})` даёт `true` для `a/b`, `a/x/b`, `ab`, `aQ/b`, `aQ/R/b` и `false` для `zzz/b`. Ни один тест в `condition.test.ts` не проверяет отрицательный кейс вида `ab`/`aQ/b` для `**` в середине — поэтому дефект зелёный.
- **fix_direction**: собрать границу сегмента для срединного `**` так, чтобы слэш перед ним не терялся (фрагмент должен требовать разделитель либо целиком поглощать «слэш + ноль или более сегментов»), и завести в тестах обязательные отрицательные кейсы на каждую позицию `**` (начало, середина, конец): склейка соседних сегментов без разделителя и совпадение по префиксу сегмента.

### claude-08

Комментарий рядом описывает намерение точнее реализации: «can point at any already-visited **ancestor**», а проверяется весь список посещённых.

- **in_scope**: да
- **anchor**: `packages/projects-tree/src/projects/discovery/walker.ts:139-147`
- **evidence**:
  ```ts
  if (visitedIdentities.has(identity)) {
    return { diagnostic: { rootId, path, kind: 'cyclicSymlink', message: `Symlink cycle detected at ${path}` } };
  }
  ```
- **verification**: confirmed
- **verification_note**: подтверждено чтением: множество создаётся один раз на `walkRoot`, пополняется в `readDirectoryTracked` для каждого чтения и никогда не сокращается при возврате из ветви; проверки «identity принадлежит цепочке предков» в коде нет

- `claude-R2` | `not` с пустым `of` даёт вакуумную истину и правило срабатывает на всём | Отклонено: `rules.schema.json` задаёт `"of": { ..., "minItems": 1 }`, поэтому из файла правил пустой `of` не приходит. Остаётся достижимым только программной сборкой `Rule[]` в обход загрузчика — внутренний, не пользовательский путь.
- `claude-R3` | `skip: true` вместе с `stopDescend: true` теряет остановку спуска, потому что `normalizeVerdict` обнуляет `stopDescend` | Отклонено чтением `walker.processNode`: `verdict.skip.value` возвращает `undefined` до вычисления `canDescend`, поэтому спуска в пропущенный узел не происходит и обнуление `stopDescend` ни на что не влияет.
