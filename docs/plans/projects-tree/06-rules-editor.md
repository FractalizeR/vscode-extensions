# Этап 06. Редактор правил (webview)

Ревизия 3 после round 02: превью показывает вердикт по каждому полю (понятие «ось» убрано);
протокол научился сохранять действия и защищать от записи поверх изменённого файла.

Цель: правила настраиваются визуально, с превью того, как изменится дерево. Второй релиз.

Мотив: приоритетный список условий отлаживать по JSON неудобно именно потому, что порядок значим —
пользователю нужно видеть, какое правило сработало на конкретном узле.

## Пакет 06-A. Стек webview

Файлы: `packages/projects-tree/webview/{package.json,vite.config.ts,src/main.ts}`,
`src/editor/rules-editor/panel.ts`.

Решения:
- редактор правит **файл правил**, а не `settings.json` (см. [00-overview.md](00-overview.md));
  сохранение — запись файла с валидацией до записи, без частично применённого состояния;
- **не** `@vscode/webview-ui-toolkit` — задеприкейчен 01.01.2025, репозиторий заархивирован (под ним
  умер FAST Foundation). Берём [VSCode Elements](https://vscode-elements.github.io/) на Lit: он
  использует переменные тем VS Code, поэтому редактор выглядит родным без своей палитры;
- webview собирается отдельным Vite-конфигом в тот же `dist`, CSP строгий, `nonce` на скрипты,
  `localResourceRoots` ограничены;
- состояние сохраняется через `webview.setState`, чтобы скрытие панели не теряло несохранённые
  правки.

DoD: панель открывается, выглядит в соответствии с активной темой, CSP без ослаблений, ресурсы не
загружаются извне.

## Пакет 06-B. Протокол между расширением и webview

Файлы: `src/editor/rules-editor/{protocol.ts,host.ts}`, `webview/src/api.ts`.

```ts
type ToWebview =
  | { type: 'rulesLoaded'; rules: Rule[]; actions: ActionDefinition[]; diagnostics: Diagnostic[] }
  | { type: 'previewResult'; nodes: PreviewNode[]; truncated: boolean }
type FromWebview =
  | { type: 'requestPreview'; rules: Rule[] }
  | { type: 'saveRules'; rules: Rule[]; actions: ActionDefinition[]; baseMtime: number }
```

- **Сообщения из webview — недоверенный ввод**: валидируются той же валидацией из этапа 02, прежде
  чем попасть в файл. Тип на границе не гарантирует форму данных;
- `saveRules` несёт и **действия**: редактор правит их наравне с правилами (правило ссылается на
  `ActionDefinition.id`), а протокол ревизии 2 сохранять их не умел — редактор действий из 06-C был
  нереализуем;
- `baseMtime` — `mtime` файла на момент чтения; расширение отказывает в записи, если файл изменился
  после этого. Единственный писатель файла — расширение, но писателей внутри него трое: редактор,
  «Hide» и визард;
- превью считается на стороне расширения (ядро уже умеет классифицировать) по **уже раскрытым**
  узлам, без обхода ФС на каждое нажатие клавиши; запросы дебаунсятся. Граница применимости названа
  явно: правило, влияющее только на нераскрытые ветки, в превью не проявится — панель показывает это
  сообщением, а не молча даёт неполную картину (находка ревью).

DoD: заведомо некорректное сообщение из webview не попадает в настройки и даёт диагностику.

## Пакет 06-C. UI редактора

Файлы: `webview/src/components/*`.

- список правил с drag-and-drop переупорядочиванием — порядок и есть главная семантика;
- редактор условия: дерево `all`/`any`/`not` с листьями-условиями, без ручного ввода JSON;
- проверка регулярки на живых именах узлов прямо в редакторе;
- **панель превью**: дерево справа; для выбранного узла показывается вердикт **по каждому полю**
  (`skip`, `stopDescend`, `project`, `primaryAction`, `highlight`, `tags`) и правило-источник по
  каждому — поле `byRule`. Разбивка по полям, а не по группам: first-match применяется к полю
  (02-A), и группировка врала бы ровно там, где правила задают разные поля;
- редактор действий и привязка основного действия к правилу;
- кнопка «Восстановить дефолтные правила».

DoD: правило создаётся целиком мышью, порядок меняется drag-and-drop, превью отражает изменение до
сохранения, выбор узла показывает сработавшее правило.

## Тестовый план этапа

Unit: валидация входящих сообщений протокола; расчёт превью по снимку дерева; сериализация правил
туда-обратно без потерь.
Интеграционные: открытие панели, сохранение правил через протокол меняет настройки.
Ручные: сборка правила мышью, переупорядочивание, превью, поведение при невалидной регулярке.
