## Куда смотреть в первую очередь

Это гипотезы оркестратора, а не ограничение области. Coverage фиксируйте по всему диффу.

- **Швы между пакетами.** `src/extension.ts` собирает граф объектов и его писал оркестратор, а
  `item.ts`/`provider.ts`/`decorations/**` — отдельный исполнитель, `test/integration/**` — третий,
  `tools/check-l10n.ts` — четвёртый. Вопрос, на который нужен ответ: **какую форму входа не покрыл
  ни один пакет.** Один такой шов уже сработал (интеграционные тесты писались под конструктор
  `ProjectsTreeProvider` с 6 аргументами, пакет 03-B добавил обязательный 7-й; поймал компилятор).
- **Вызывается ли новый код из production.** Обязательный пункт приёмки в этом репозитории после
  round 05: для каждого нового экспортируемого символа должен существовать вызов вне тестов.
  `knip` это ловит лишь частично — он не видит вызовов, которые делает другой инструмент.
- **`ExpansionStore` и `collapsibleState`.** Факт 41: `collapsibleState` из `getTreeItem` — только
  дефолт для узла, впервые появившегося в данном view; уже существующий узел платформа не
  переопределяет. Предикат `isExpanded` умеет только поднять дефолт до `Expanded`. Проверьте, что
  из этого не следует незамеченного расхождения: ключ, под которым пишется раскрытие
  (`treeElementKey`), обязан совпадать с `TreeItem.id`, иначе фича молча не работает вовсе.
- **Декорации.** Факт 7: бейдж длиннее двух символов роняет валидацию платформы и декорация
  отбрасывается **целиком, вместе с цветом**; пустая декорация запрещена там же. Единица подсчёта —
  code points, и она должна совпадать с той, что уже использует ядро
  (`src/projects/classification/validation.ts`). Факт 9: `propagate` требует самостоятельно
  сигналить `onDidChangeFileDecorations` для предков. `propagate` включён безусловно — это
  интерпретация неоднозначной формулировки плана, а не цитата; оцените её отдельно.
- **Два view.** Факт 5: это два разных view с разными id, поэтому `viewsWelcome`, `menus` и
  `activationEvents` дублируются. Режим `none` должен гасить оба. Проверьте, что ничто не забыто и
  что провайдер зарегистрирован корректно на оба id.
- **Тесты, которые проверяют сами себя.** В репозитории это названный класс отказа. В этом диффе
  четыре новых проверки: `tools/check-l10n.ts`, `tools/check-chain.test.ts`,
  `tools/compat-floor.test.ts`, `src/editor/tree-view/manifest-contract.test.ts`. Для каждой
  спросите: сравнивает ли она два **независимых** источника, или один сгенерирован из другого
  (тогда она всегда зелёная)? Может ли она пройти при удалённом защищаемом поведении?
- **Локализация.** Факт 49: ключ бандла — сама английская строка. Факт 50: базовый бандл в рантайме
  не нужен. Экстрактор ходит по AST TypeScript; проверьте формы вызова `l10n.t`, которые он
  обязан отвергать громко, а не пропускать молча.
- **CI и тулинг.** Джоба `integration-test`, `xvfb-run -a` только на Linux (факт 55), кэш редактора,
  игнор `@vscode/test-electron` в `knip.json`, `**/.vscode-test/**` в `eslint.config.mjs`.

## Формат

Пишите в `docs/plans/projects-tree/review-06/findings/<reviewer>.md` строго по
`dvizh-vr-review/reference/finding-schema.md`: поля находки, порядок по убыванию severity, затем
секция coverage, затем секция refuted одной строкой на находку. `depth`: тщательно —
приоритет корректности и надёжности над стилем.

**Поле `reviewer` называет фактического исполнителя.** Не подписывайте результат чужим именем.

Отдельно и в первую очередь сообщайте:
- любое решение, опирающееся на утверждение об API, которого нет в `api-facts.md`;
- любую строку `api-facts.md`, которая при проверке расходится с источником — таких уже нашлось
  несколько, и это самая ценная категория находок;
- любое место, где тест проходит при удалённом защищаемом поведении.

Прогонять `pnpm check` не нужно — он зелёный (388 тестов), как и `test:integration` (6 тестов в
живом редакторе). Если считаете, что проверка зелёная неправомерно, — это находка.
