# Сведение ревью реализации этапа 01 — round 04

Ревьюеры: `claude` (24 находки, 23 confirmed, 5 refuted), `codex` (12 находок, 11 confirmed,
8 refuted). Материал — рабочее дерево, `pnpm check` зелёный на входе и на выходе ревью.

Раунд оправдал себя: **центральная граница архитектуры не работала**, и это не было видно ни по
зелёному `pnpm check`, ни по зелёной негативной проверке.

## Группировка по механизму

### G1. Правила границ написаны против имён, а проверялись против самих себя

Дефекты: `no-vscode-in-core` не матчит резолвленный путь `@types/vscode` (claude-01, HIGH); каталог
под `src/`, не входящий в `projects/` или `editor/`, не покрыт ни одним правилом (claude-02, HIGH);
`no-node-builtins-in-core-logic` запрещает ядру **все** builtins, хотя объявлен про `node:fs`
(claude-15); `webview-is-isolated` пропускает импорт точки входа расширения (codex-04).

Общий механизм: правила писались на будущую раскладку и верифицировались фикстурами, написанными
под эти же правила. Фикстура подтверждала формулировку правила, а не защиту границы — тавтология,
дающая зелёный результат при реальном нарушении.

**Решение:** правила проверяются на **реальном коде пакета**, а не только на фикстурах: в негативную
проверку добавляется нарушитель, размещённый внутри `packages/projects-tree/src`, с обычным
импортом. Матчинг внешнего модуля переводится с `to.path` на форму, устойчивую к резолву типов
(проверить `to.dependencyTypes` и совпадение по `@types/vscode`), и результат подтверждается
прогоном, а не чтением. Плюс правило-«последний рубеж»: всё под `src/`, что не `projects/` и не
`editor/`, — нарушение раскладки.

### G2. Негативная проверка проверяет концепты, а не правила

Дефекты: 5 из 6 попарных правил `no-sibling-internals` можно удалить, проверка останется зелёной
(claude-03, HIGH; codex-03); исключения из правил ничем не утверждены — контрольный образец
`fileSystem.ts` не проверяется (claude-06).

**Решение:** сверка идёт по полным именам всех правил, а не по префиксу до `:`; для каждого правила
утверждается и нарушитель (должен падать), и контрольный образец (не должен). Список правил берётся
из конфига, а не хардкодится числом 6 — иначе добавленное правило останется без негативной пробы.

### G3. Релизный процесс не связан с версией

Дефекты: `version: 0.0.0` в манифесте не синхронизируется с тегом — любой релиз выйдет как 0.0.0
(claude-04, HIGH; codex-02, HIGH); `release.yml` и `publish.yml` не прогоняют `pnpm check`, то есть
тег публикует невалидированный код (claude-10); корневой `pnpm package`, на который ссылается план,
отсутствует (codex-07); Dependabot с `patterns: ['*']` снимет намеренный точный пин
`@types/vscode` (claude-08); `awk` подставляет версию в регэксп без экранирования (claude-21).

Механизм: 01-D зафиксировал версию, 01-E написал релиз от тега, мост между ними не сделал никто —
это шов между пакетами работ, а не дефект одного из них. Changesets план упоминал, но ни один
пакет его не внедрил.

**Решение:** внедрить Changesets как владельца версии либо выводить версию из тега при сборке
релиза (выбрать одно и записать); `release.yml`/`publish.yml` прогоняют `pnpm check` перед
публикацией; `@types/vscode` исключается из Dependabot явным `ignore`, потому что его пин —
осознанное решение, а не устаревшая зависимость.

### G4. CI не проверяет того, что план требовал

Дефекты: проверка состава `.vsix` через `vsce ls`, прямо предписанная DoD 01-D, не реализована
нигде (claude-09; codex-05); `tools/**/*.mjs` не покрыт ни typecheck, ни типизированным линтингом
(claude-13); `.prettierignore` выводит `docs/**` из `format:check` целиком, вместе с
`docs/architecture.md` (claude-12; codex-09); двойной прогон CI на каждый коммит в PR (claude-18).

**Решение:** allowlist состава `.vsix` — отдельный шаг CI, сверяющий вывод `vsce ls` с эталонным
списком; исключение `docs/**` сужается до `docs/plans/**` (планы правятся вручную и Prettier им не
нужен, а `architecture.md` — обычный документ); `tools/**` включается в typecheck.

### G5. Секреты и неверсионированный код в публикации

Дефекты: `pnpm dlx ovsx` тянет неверсионированный пакет и исполняется, когда в `env` джобы лежат
оба токена (codex-01, HIGH); оба PAT видны всем шагам джобы, включая `install` и `package`
(claude-05).

**Решение:** `ovsx` закрепляется точной версией как devDependency (или вызывается с явной версией);
каждый токен пробрасывается **в тот единственный шаг**, которому он нужен, а не в `env` джобы.

### G6. Документы расходятся с фактом

Дефекты: `AGENTS.md` описывает как существующее то, чего в репозитории нет (claude-11); правила про
integration tests двусмысленны (codex-11); `activationEvents: []` расходится с планом, расхождение
не записано (claude-14); DoD «видимая дерево-заглушка» невыполним при пустом `contributes`
(codex-08); предупреждение про symlink на Windows не в README, как требует DoD 01-C (claude-17;
codex-12).

**Решение:** раскладка в `AGENTS.md` помечается как целевая с указанием, что каталоги вводит этап 02;
DoD 01-D в плане правится под факт (заглушка не имеет вкладов и потому невидима — проверка
установки подтверждает только упаковку и активацию); предупреждение про Windows добавляется в README.
