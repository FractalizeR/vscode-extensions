### claude-01

- **reviewer**: claude
- **severity**: HIGH
- **kind**: contract
- **domain**: reliability
- **title**: Факт 5 ложен: длина `FileDecoration.badge` ограничена API двумя графемами, и нарушение отбрасывает декорацию целиком
- **mechanism**: `api-facts.md` строка 5 утверждает «`FileDecoration.badge` не имеет ограничения длины в API», ссылаясь на `extHostDecorations.ts:104`, где действительно проверяется только тип. ### claude-02

- **reviewer**: claude
- **severity**: HIGH
- **kind**: contract
- **domain**: security
- **title**: `substitute()` возвращает недоверенным весь результат подстановки, поэтому квотирование применяется не к тому уровню
- **mechanism**: контракт 02-E — `substitute(template, node): Untrusted<string>` и `quoteForShell(value, shell): string`. Подстановка отдаёт **целую строку команды** (шаблон + вставленные значения) одним недоверенным значением; квотировать её как единое целое нельзя — заквотированная целиком командная строка перестаёт быть командой (превращается в одно слово). Единственный способ выполнить контракт — снять обёртку и склеить, то есть ровно то, что обёртка обещала сделать невозможным. Правильная граница — квотировать **каждое подставляемое значение до сборки**, а недоверенным считать значение переменной, а не результат. Плюс `Untrusted<T> = { readonly untrusted: T }` — структурный, а не номинальный тип: любой объект с полем `untrusted` подходит, и распаковка — обычное обращение к полю без единого маркера в коде.
- **trigger**: воспроизводится в нормальной работе — любое действие `terminal` с `${name}`/`${path}` из склонированного репозитория
- **in_scope**: да
- **anchor**: контракт `substitute`/`quoteForShell`/`Untrusted<T>` в `02-core.md` пакет 02-E; применение в `04-actions.md` пакет 04-A
- **evidence**: `02-core.md:193-196`
  ```ts
  type Untrusted<T> = { readonly untrusted: T }        // номинальная обёртка
  function substitute(template: string, node: ClassifiedNode): Untrusted<string>
  function quoteForShell(value: Untrusted<string>, shell: ShellKind): string
  ```
  и `04-actions.md:24-25`: «подстановки проходят через `quoteForShell` под фактический шелл»
- **verification**: confirmed
- **verification_note**: дефект в самих сигнатурах плана, кода нет; проверяется чтением контракта, а не запуском
- **fix_direction**: перенести границу доверия на уровень значения переменной: подстановка принимает уже закодированные под целевой контекст значения, а сборка строки становится единственной операцией, которая умеет соединять шаблон с квотированными значениями; обёртку сделать действительно номинальной (брендированный тип без публично читаемого поля) и запретить её распаковку вне модуля квотирования — иначе тип не даёт ничего, кроме документации

### claude-03

- **reviewer**: claude
- **severity**: HIGH
- **kind**: contract
- **domain**: security
- **title**: Шелл действия `terminal` в общем случае неопределим, а `reuse: true` отправляет строку в шелл, который расширение не создавало
- **mechanism**: 04-A определяет шелл «по `terminal.integrated.defaultProfile` и платформе». Настройка может быть не задана (VS Code выбирает шелл сам), может указывать на профиль с произвольным `path` (fish, nu, xonsh, git-bash), может быть переопределена профилем воркспейса. `quoteForShell(value, shell)` при неверно угаданном `shell` — не защита, а ложное чувство защиты: правила квотирования POSIX-шеллов, PowerShell и cmd несовместимы, и заквотированное «под bash» значение в PowerShell/cmd снова становится синтаксисом. Хуже: `ActionSpec.terminal` имеет `reuse?: boolean` (02-E), то есть строка отправляется в **уже существующий** терминал, чей шелл расширению неизвестен принципиально. Механизм отправки — `sendText`, который по `vscode.d.ts` пишет прямо в stdin pty; значит исполняется не только `\n`, но и `\r`, а запрет плана распространяется только на `\n`.
- **trigger**: воспроизводится в нормальной работе — Windows с PowerShell-профилем по умолчанию либо повторное использование терминала, плюс каталог в чужом клоне с именем, содержащим `` ` ``, `$(`, `"` или `\r`
- **in_scope**: да
- **anchor**: `04-actions.md` пакет 04-A (исполнитель `terminal`, `shellKind.ts`); `02-core.md` пакет 02-E (`ActionSpec.terminal.reuse`, запрет `\n`)
- **evidence**: `vscode.d.ts:7723-7731`
  ```ts
  /** Send text to the terminal. The text is written to the stdin of the underlying pty process (shell). */
  sendText(text: string, shouldExecute?: boolean): void;
  ```
  Есть штатная альтернатива без шелл-строки — `vscode.d.ts:7941`: `executeCommand(executable: string, args: string[]): TerminalShellExecution;` и `TerminalOptions.shellPath`/`shellArgs` (`vscode.d.ts:12476-12482`)
- **verification**: confirmed
- **verification_note**: `executeCommand(executable, args)` требует shell integration и не всегда доступен, но `createTerminal({ shellPath, shellArgs })` доступен всегда и снимает вопрос квотирования полностью
- **fix_direction**: перестать строить шелл-строку там, где это возможно: передавать исполняемое и аргументы раздельно (созданный расширением терминал с явным `shellPath`/`shellArgs` либо argv-форма shell integration), а `sendText` со квотированием оставить только для случая, где шелл создан этим же расширением и потому известен; для `reuse` — либо запретить подстановки, либо отказаться от режима; в запрет включить весь класс исполняющих символов (`\n`, `\r`, U+2028/U+2029), а не один

### claude-04

- **reviewer**: claude
- **severity**: HIGH
- **kind**: contract
- **domain**: architecture
- **title**: `descend` невыразим правилами: `stop` требует знания вердикта другой оси, `submodules` — чтения файла, поэтому «сахар, а не второй механизм» неверно
- **mechanism**: 00-overview и 02-C объявляют, что `descend` разворачивается в правило оси `visibility` с условием `inRoot`. Но `Condition` вычисляется по `NodeFacts` (`rootId`, путь, имя, глубина, `entries`) и не имеет доступа к вердикту оси `identity`. Семантика `stop` — «остановиться, **дойдя до проекта**», то есть предикат по вердикту `identity.project`. Выразить его правилом можно только продублировав определение проекта (`hasChild: ['.git', '.idea']`) в правило видимости — и тогда изменение пользователем правил проектности молча расходится с остановкой обхода, что и есть «два независимых механизма», от которых план отказывался. Режим `submodules` не выразим вовсе: он требует прочитать `.gitmodules` и перечислить объявленные пути, а такого вида условия в закрытом union нет — план и сам вводит для него отдельную функцию `readSubmodulePaths` в `discovery/`. Кроме того условие `inRoot` истинно для **каждого** узла корня, поэтому развёрнутое правило высказывается по оси `visibility` обо всех узлах и, по first-match, отменяет любое правило ниже себя — включая дефолтные `skip` мусорных папок, если те окажутся ниже.
- **trigger**: воспроизводится в нормальной работе — дефолт `descend: 'stop'` плюс любое пользовательское изменение правила проектности; либо `descend: 'submodules'`
- **in_scope**: да
- **anchor**: контракт `expandRootSugar` / `descend` в `02-core.md` пакет 02-C и `00-overview.md` раздел «Корни и обход внутрь проектов»
- **evidence**: `02-core.md:109-110`
  ```ts
  function expandRootSugar(root: RootConfig): readonly Rule[]   // сахар -> правила оси visibility
  function readSubmodulePaths(projectPath: string): Promise<readonly string[]>
  ```
  плюс `00-overview.md:113-116`: «При загрузке он разворачивается в правило по оси `visibility` с условием `inRoot`»; `Condition` (`00-overview.md:64-71`) не содержит ни ссылки на вердикт, ни чтения файлов
- **verification**: confirmed
- **verification_note**: сопоставление двух контрактов плана между собой; из тестового плана 02 видно то же — «разбор `.gitmodules`» тестируется отдельно от «разворачивания сахара»
- **fix_direction**: признать, что режим корня — не сахар, а вход обхода, и назвать его местом в обходе явно; либо, если сохранять выражение через правила, ввести в вердикт видимости зависимость от вердикта проектности (порядок вычисления осей становится частью контракта) и отдельный вид условия для «объявлен в `.gitmodules`»; в любом случае зафиксировать, где именно развёрнутое правило встаёт относительно дефолтных `skip`, потому что условие `inRoot` перекрывает всё, что ниже
