# Этап 04. Действия, их запуск и быстрый выбор проекта

Ревизия 3 после round 02: команда в терминал по умолчанию **вставляется, но не исполняется**; шелл
задаётся действием, а не угадывается; переиспользование терминала убрано; закрыты виды `uri` и
`command`; названо ограничение Windows для `.cmd`-обёрток; session-кэш быстрого выбора получил
инвалидацию; отмена берётся из этапа 02, а не из 07.

## Пакет 04-A. Исполнители действий

Файлы: `src/editor/commands/actions/{runner.ts,openFolder.ts,terminal.ts,process.ts,uri.ts,
vscodeCommand.ts,shellKind.ts}`.

```ts
interface ActionRunner { run(action: ActionDefinition, node: ClassifiedNode): Promise<void> }
```

Исполнители по видам `ActionSpec` из этапа 02:

- `openFolder` — `vscode.commands.executeCommand('vscode.openFolder', uri, { forceNewWindow })`.
  При `window: 'auto'` — новое окно, если текущее уже имеет открытую папку. Если в проекте есть
  `.code-workspace`, открывается он (поведение прототипа);
- `terminal` — `window.createTerminal({ cwd, shellPath })` + `sendText(text, execute)`. Это кейс
  «запустить OpenCode в папке проекта», и единственный вид действия, где строка попадает в shell.
  Три решения вместо одного «квотировать»:
  - **`execute` по умолчанию `false`** (факт 11): команда вставляется в терминал, пользователь видит
    подставленный путь и нажимает Enter сам. Имя каталога со спецсимволами перестаёт быть
    исполнением без ведома пользователя — это снимает основную тяжесть вектора, а не только
    затрудняет его;
  - **шелл задаётся действием** и передаётся в `shellPath` (факт 12), поэтому правило квотирования
    известно. Ревизия 2 определяла его по `terminal.integrated.defaultProfile` — недостоверно, и
    неверная догадка означала неверное квотирование;
  - **переиспользование терминала убрано**: отправка в уже открытый чужой шелл ломает предположение
    о правилах квотирования. `shellIntegration` заменой не является — он может не активироваться
    никогда (факт 13);
- `process` — запуск внешнего редактора (`phpstorm`, `idea`) отдельным процессом, detached.
  Аргументы передаются массивом, никогда не собираются в строку для shell. **Ограничение Windows
  названо явно:** `.cmd`/`.bat`-обёртки (а `phpstorm.cmd` именно такая) не запускаются без
  `shell: true`, то есть массив аргументов там не защищает. Решение: такие цели требуют явно
  объявленного шелла и квотирования под `cmd` — то есть трактуются как `terminal`, а не как
  `process`; без объявленного шелла запуск отвергается с внятным сообщением;
- `uri` — `vscode.env.openExternal`; подстановки рендерятся с целевым контекстом `uri`
  (процентное кодирование), а не конкатенируются;
- `command` — вызов произвольной команды VS Code. **Аргументы тоже проходят рендер:** подстановка в
  `args` — такой же недоверенный ввод, и ревизия 2 этот вид из контракта упускала.

Граничные случаи: команда не найдена в PATH (внятная ошибка, не молчание); процесс упал сразу; путь
с пробелами, кавычками, `;`, backtick, `%…%`, юникодом; `\n` в имени каталога; `.cmd`-цель без
объявленного шелла; действие применимо, но проект уже удалён; `primaryAction` ссылается на
несуществующий id (валидация этапа 02 не даёт этому дойти до рантайма, но исполнитель обязан пережить
рассинхрон).

Отдельное признание: `openFolder` с `window: 'current'` перезагружает окно и убивает extension host.
Незавершённые операции не переживают перезагрузку — состояние, которое должно уцелеть, не держится в
памяти.

DoD: каждый вид действия проверен вручную на живой машине; каталог с именем, содержащим `;` и
пробел, даёт в терминале корректно квотированную команду, которая **не исполнена** до нажатия Enter;
`execute: true` требует явного включения в действии.

## Пакет 04-B. Настройки, их scope и доверие

Файлы: вклады `configuration` в `package.json`, `src/editor/configuration/{settings.ts,rulesFile.ts}`.

Сведённый список настроек и их scope — **весь**, чтобы scope назначался осознанно, а не одному
пункту из шести:

| настройка | тип | scope | почему |
|---|---|---|---|
| `projectsTree.roots` | array | `machine` | направляет обход по диску; переопределение из чужого воркспейса — чтение произвольных каталогов |
| `projectsTree.maxDepth` | number | `machine` | ограничитель стоимости обхода |
| `projectsTree.location` | enum | `window` | чисто визуальная, безопасна для воркспейса |
| `projectsTree.defaultAction` | string | `machine` | ссылается на действие, то есть на исполнение |
| `projectsTree.favicon.*` | | `machine` | этап 07 |

Правила и действия в настройках **не живут вовсе** — они в отдельном файле правил
([00-overview.md](00-overview.md)): чужой репозиторий не может ни подсунуть команду, ни скомпилировать
регулярку с катастрофическим бэктрекингом в extension host.

Два разных гейта, которые прежняя ревизия смешивала:
- **доверие окна** (Workspace Trust) — объявлено в манифесте на этапе 01 как ограниченная
  поддержка; в недоверенном окне дерево работает, действия с исполнением (`terminal`, `process`)
  недоступны;
- **источник настройки** (`scope`) — таблица выше.

**Ветка, которой не было в модели угроз до round 03:** `scope: machine` означает «только user
settings **или remote settings**» (факт 18) — прошлая ревизия читала это как «только user». Значит
в remote-сценарии (SSH, dev container, WSL) `roots`, `maxDepth` и дефолтное действие приходят из
настроек удалённой машины, которую пользователь мог не настраивать сам. Требование: действия с
исполнением в remote-окне подчиняются тому же гейту доверия, что и в недоверенном воркспейсе, а
источник значения (`ConfigurationTarget`) при расхождении показывается пользователю. Проверяется
вручную в remote-окне; автоматизировать это в первом релизе не будем.

DoD: попытка переопределить `roots` в workspace-настройках игнорируется; в недоверенном окне дерево
показывается, а `terminal`/`process` не запускаются и объясняют почему.

## Пакет 04-C. Подключение к UI

Файлы: `package.json` (`commands`, `menus`, `keybindings` — на **оба** id view, см. 03-C),
`src/editor/commands/{register.ts,actionPicker.ts}`.

- клик по узлу-проекту → `projectsTree.runPrimaryAction`: берёт поле `primaryAction` вердикта,
  иначе дефолт из настроек;
- фиксированные пункты контекстного меню: «Open in New Window», «Open in Current Window»,
  «Actions…», «Hide», «Remove Root»;
- «Actions…» → QuickPick из действий, чей `appliesTo` подходит узлу. Это обход ограничения
  платформы: динамически добавить пункты в меню невозможно (факт 20);
- `projectsTree.runAction` принимает id действия аргументом — на неё можно назначить свой
  keybinding, и любимое действие получает горячую клавишу без пункта в меню.

DoD: клик открывает проект согласно настройке; «Actions…» показывает только применимые действия;
keybinding на конкретное действие работает; все пункты меню видны в обоих режимах размещения.

## Пакет 04-D. Быстрый выбор проекта

Файлы: `src/editor/commands/quickOpen.ts`.

- команда «Open Project…» — QuickPick с fuzzy-поиском по проектам; единственный способ работы в
  режиме размещения `none`;
- **в первом релизе список строится обходом по требованию**, с прогрессом и отменой (порт отмены —
  02-C, а не этап 07: он нужен уже здесь). Фонового полного обхода нет, поэтому первый вызов на
  большом дереве занимает время — честная цена отсутствия кэша;
- результат переиспользуется в пределах сессии, но **инвалидируется** при смене правил, корней или
  `maxDepth` — иначе это кэш без инвалидации, то есть ровно то, что вынесено в этап 07. Инвалидация
  общая с `NodeRegistry` (03-A).

DoD: QuickPick находит проект по частичному имени; отмена во время сбора списка прекращает чтение
ФС (счётчик вызовов порта); правка файла правил сбрасывает список; в режиме `none` команда —
достаточный способ пользоваться расширением.

## Пакет 04-E. Управление корнями и скрытием

Файлы: `src/editor/commands/{roots.ts,hidden.ts}`.

- «Add Root…» — диалог выбора папки, запись в настройки;
- «Remove Root» — удаление с подтверждением;
- «Hide» — дописывает в начало файла правил правило с условием **`pathEquals`**, а не регуляркой:
  путь может содержать метасимволы regex, и прежняя формулировка («правило `skip` по пути») их не
  экранировала;
- перед записью проверяется, не скрыт ли узел уже правилом выше — иначе создаётся мёртвое правило;
- «Manage Hidden…» — список правил, созданных скрытием, с возможностью убрать.

DoD: скрытый узел исчезает без Reload; путь с `(` и `+` скрывается корректно; повторное скрытие
уже скрытого узла сообщает об этом; «Manage Hidden» возвращает узел.

## Тестовый план этапа

Unit: выбор основного действия (поле вердикта → настройка → дефолт); фильтрация по `appliesTo`;
рендер под каждый поддерживаемый шелл и под `uri`; отклонение `\n`; сборка аргументов `process` для
путей со спецсимволами; отказ запускать `.cmd` без объявленного шелла.
Интеграционные: регистрация команд на оба view; «Hide» меняет файл правил и дерево; «Add Root» пишет
корректный путь; недоверенное окно блокирует исполняющие действия.
Ручные: все пять видов действий на живой машине, включая OpenCode в терминале и открытие в PhpStorm;
каталог с `;` в имени.

## Решения, изменённые при реализации

Записано по факту исполнения: каждый пункт — решение, которое изменилось из-за проверенного факта
или обнаруженного ограничения, а не из-за удобства.

**В remote-окне спрашивается подтверждение, а не блокируется всё.** 04-B требовал буквально:
исполняющие действия в remote подчиняются тому же гейту, что и в недоверенном воркспейсе, то есть
недоступны. Цена буквального прочтения — расширение на любом SSH/dev-container окне теряет половину
смысла, притом что угроза здесь мягче: настройка `machine` в remote приходит с удалённой машины
(факт 18), но эту машину пользователь обычно выбирал сам. Решение: разовое подтверждение на
конкретный remote authority, согласие запоминается в `globalState`, отказ — только на сессию
(персистентный отказ означал бы, что передумать можно лишь правкой `globalState` руками). Текст
подтверждения называет `env.remoteName` и то, что настройки пришли с той машины. Точнее сказать
нечего: `WorkspaceConfiguration.inspect()` на планке 1.85 не различает remote и локальный user
settings — поля под это нет вовсе (факт 73), и изображать точность, которой у API нет, хуже, чем
назвать источник приблизительно.

**Вид `command` тоже под гейтом.** План перечислял `terminal` и `process`. `command` исполняет
произвольную команду редактора — это исполнение ровно в том же смысле, и оставлять его открытым
значило бы обойти собственный гейт через `ActionSpec`, который план сам же и вводит.

**Гейт не участвует ни в одном `when`, и context key под него снят.** Первая реализация завела
`projectsTree.executionAllowed` и прятала им пункты меню. Это давало замыкание, невидимое на
локальной машине (там `env.remoteName === undefined`): согласие на remote спрашивается только при
запуске действия, а действие скрыто до согласия. Решение: не гейтить меню вовсе — DoD 04-B и так
требует, чтобы в недоверенном окне действия **не запускались и объясняли почему**, то есть пункт
остаётся видимым, а объяснение даётся при клике. Ключ, `ExecutionGate.peek()` (существовавший только
ради ключа) и слушатель `onDidGrantWorkspaceTrust` (после снятия ключа он гонял полный обход диска
без наблюдаемого эффекта) удалены. Единственный вход в гейт — `check()` в момент запуска действия.

**`propagate` вернулся полем правила, а сигнал предков — нет, и граница «до корня» оказалась
невыразимой.** Долг этапа 03 закрывался парой «флаг + сигнал предков», потому что факт 9 требует
сигнала, но не говорит, что именно сигналить. Факт 62 это уточнил: предку декорация не присылается,
а вычисляется — сервис сканирует собственный кэш (`findSuperstr`) и подмешивает записи с
`bubble === true`; событие по URI самого узла уже делает `affectsResource` истинным для каждого его
предка на диске. Значит явный список предков не даёт наблюдаемого эффекта (его пробовали и убрали —
это тот же класс дефекта, за который сигнал сняли в round 06), а «поднимать только до нашего корня»
нельзя в принципе: платформа ходит по литеральной иерархии путей и о наших корнях не знает. Цена
названа прямо: правило с `propagate: true` поднимет бейдж в Explorer выше корня, если корень лежит
внутри более широкого воркспейса. Это осознанный opt-in в конкретном правиле, а не политика по
умолчанию, — тем он и отличается от того, что выключили в 03.

**Настройки `maxDepth` не существовало вовсе.** Таблица 04-B перечисляет её как действующую, но в
манифесте её не было ни в 01, ни в 03, и обход всё это время жил на внутреннем дефолте
`discoverProjectTree` (4). Настройка заведена здесь вместе с реальным пробросом; тест проверяет не
то, что функция вернула число, а то, что обход перестал читать глубже.

**`showRootNodes` в таблице scope отсутствует; оставлена `window`.** Таблица 04-B перечисляет пять
настроек и эту не называет. Она чисто визуальная (группировать ли содержимое корней) и обходом по
диску не управляет, поэтому `window` — тот же класс, что `location`.

**`ActionRunner.run` принимает `ActionRenderNode`, а не `ClassifiedNode`.** Псевдокод 04-A требовал
второе, но `rootPath` в `ClassifiedNode` нет (узел знает `rootId`, не путь корня), а рендеру он
нужен для `${rootPath}`. Конвертация — отдельный `toRenderNode`, вызываемый композиционным корнем,
который единственный знает и узел, и конфигурацию корней.

**При коллизии id встроенного и пользовательского действия побеждает файл правил.** Иначе явная,
прошедшая валидацию запись пользователя молча не делала бы ничего.

**Дефолт `projectsTree.defaultAction` — `builtin.openInNewWindow`, не `openAuto`.** Значение, которого
никто не трогал, не должно уметь перезагружать окно и убивать extension host (факт 10).

**Keybinding по умолчанию не назначен.** Контракт «горячая клавиша с заранее заданным аргументом»
(факт 29) реализован и покрыт тестами, но конкретная клавиша — выбор пользователя под его любимое
действие; занимать сочетание за него значит конфликтовать с чужими расширениями ради демонстрации.

**«Hide» работает и на папке, не только на проекте**, и пишет условие `all[inRoot, pathEquals]`.
`pathEquals` вместо регулярки — требование плана (метасимволы в пути), `inRoot` — добавка:
`pathFromRoot` относителен, и без привязки к корню одно правило скрыло бы одноимённые пути в разных
корнях. Правила, созданные скрытием, узнаются по префиксу id `projectsTree.hidden:`; отвергнуто
отдельное поле в JSON (правка схемы ради факта, нужного двум командам) и опознание по `title` — это
единственное поле, которое человек правит руками.

**`RawActionSpec` и `ActionSpec` остались двумя объявлениями.** Докомментарий `rules-file.ts` обещал
свести их в этом этапе; свести нельзя — `actions/` уже зависит от `classification/`, обратное ребро
даёт цикл, который ловит `no-circular`. Вместо сведения заведена тип-левел проверка совместимости:
расхождение форм перестаёт быть молчаливым и ломает компиляцию.

**Имена файлов — kebab-case**, вопреки `camelCase` в списках файлов этого документа: в пакете уже
сложилась первая конвенция (`add-root.ts`, `open-project.ts`), и две в одной папке хуже любой одной.

## Решения, изменённые по итогам ревью round 07

Полный разбор — [review-07/REPORT.md](review-07/REPORT.md); здесь только то, что меняет решения
этого этапа.

**Согласие на исполнение в remote больше не переживает сессию, и факт 72 опровергнут.** Решение
«разовое подтверждение на конкретный remote authority» опиралось на то, что `env.remoteName`
идентифицирует машину. Не идентифицирует: документация называет его значениями `wsl` и `ssh-remote`
— это класс транспорта, и согласие, данное одному SSH-серверу, молча распространялось бы на все.
Документированного способа получить идентичность конкретного хоста на планке 1.85 не нашлось
(проверено, отрицательный факт 86). Поэтому согласие живёт в памяти гейта: в новой сессии
спрашивается заново. Цена названа — лишний вопрос раз в сессию; альтернатива (запомнить по классу
транспорта) даёт разрешение, которого пользователь не давал.

**`cwd` и `terminalName` рендерятся целью `literal`, и контракт в ядре исправлен.** Докомментарий
`ActionSpec.terminal.cwd` (написан на этапе 02) предписывал цель `shell`; исполнитель выполнил
букву, тест закрепил результат — и рабочий каталог получал кавычки шелла в имени, потому что
`TerminalOptions.cwd` никакому шеллу не отдаётся. Правка одного места исполнения оставила бы мину в
тексте контракта, поэтому исправлены оба.

**Кнопка Refresh идёт через единый путь перезагрузки.** Она вызывала только перерисовку дерева, а
перечитывание файла правил, пересборка реестра действий и инвалидация кэшей жили в обработчике смены
настроек. Обещание «правка файла подхватывается на следующем refresh» при этом не выполнялось именно
кнопкой. Теперь у перезагрузки один вход, и им пользуются все три источника: команда, смена настроек
и запись файла правил из Hide/Manage Hidden.

**Условия `appliesTo` у действий проходят ту же валидацию, что и условия правил.** Screening
сложности регулярок защищал только `rules[].when`; через соседнее поле того же файла его можно было
обойти, а прервать синхронную регулярку в Node нечем (факт 26).

**Названия встроенных действий переводятся в точке показа, а заголовок скрытого правила не пишется
на диск вовсе.** Встроенные действия объявлены в ядре, которому `vscode` запрещён, поэтому перевод
живёт в адаптере; встроенное действие опознаётся по ссылке на объект, а не по id — пользовательское
действие, переопределившее встроенный id, показывает свой заголовок дословно. Заголовок правила от
«Hide» собирается из его же условия `pathEquals` при отображении: записанный в файл, он застыл бы в
языке, который был активен в момент скрытия.

**Защита файла правил по `mtime`: окно сужено, блокировки нет.** Повторная проверка перенесена
вплотную к подмене файла, но гонка двух писателей остаётся выразимой. Блокировка — новый механизм со
своим протуханием и разблокировкой после падения окна; её место в этапе 06, который умножает число
писателей файла. Ограничение названо в докомментарии `writeRulesFile` и в
[00-overview.md](00-overview.md), без преувеличения гарантии.

**`maxDepth` объявлен целым, «Remove Root» достижим без узла-группы.** Манифест разрешал дробное
значение, которое рантайм молча заменял дефолтом; «Remove Root» существовал только в меню
синтетического узла, которого нет при единственном корне и при `showRootNodes: never` — теперь
команда без аргумента предлагает выбор корня.
