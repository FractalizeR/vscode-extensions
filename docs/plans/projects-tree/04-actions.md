# Этап 04. Действия, их запуск и быстрый выбор проекта

Ревизия 3 после round 02: команда в терминал по умолчанию **вставляется, но не исполняется**; шелл
задаётся действием, а не угадывается; переиспользование терминала убрано; закрыты виды `uri` и
`command`; названо ограничение Windows для `.cmd`-обёрток; session-кэш быстрого выбора получил
инвалидацию; отмена берётся из этапа 02, а не из 07.

## Пакет 04-A. Исполнители действий

Файлы: `src/editor/commands/actions/{runner.ts,openFolder.ts,terminal.ts,process.ts,uri.ts,
vscodeCommand.ts,shellKind.ts}`.

```ts
interface ActionRunner { run(action: ActionDefinition, node: ClassifiedNode): Promise<void> }
```

Исполнители по видам `ActionSpec` из этапа 02:

- `openFolder` — `vscode.commands.executeCommand('vscode.openFolder', uri, { forceNewWindow })`.
  При `window: 'auto'` — новое окно, если текущее уже имеет открытую папку. Если в проекте есть
  `.code-workspace`, открывается он (поведение прототипа);
- `terminal` — `window.createTerminal({ cwd, shellPath })` + `sendText(text, execute)`. Это кейс
  «запустить OpenCode в папке проекта», и единственный вид действия, где строка попадает в shell.
  Три решения вместо одного «квотировать»:
  - **`execute` по умолчанию `false`** (факт 11): команда вставляется в терминал, пользователь видит
    подставленный путь и нажимает Enter сам. Имя каталога со спецсимволами перестаёт быть
    исполнением без ведома пользователя — это снимает основную тяжесть вектора, а не только
    затрудняет его;
  - **шелл задаётся действием** и передаётся в `shellPath` (факт 12), поэтому правило квотирования
    известно. Ревизия 2 определяла его по `terminal.integrated.defaultProfile` — недостоверно, и
    неверная догадка означала неверное квотирование;
  - **переиспользование терминала убрано**: отправка в уже открытый чужой шелл ломает предположение
    о правилах квотирования. `shellIntegration` заменой не является — он может не активироваться
    никогда (факт 13);
- `process` — запуск внешнего редактора (`phpstorm`, `idea`) отдельным процессом, detached.
  Аргументы передаются массивом, никогда не собираются в строку для shell. **Ограничение Windows
  названо явно:** `.cmd`/`.bat`-обёртки (а `phpstorm.cmd` именно такая) не запускаются без
  `shell: true`, то есть массив аргументов там не защищает. Решение: такие цели требуют явно
  объявленного шелла и квотирования под `cmd` — то есть трактуются как `terminal`, а не как
  `process`; без объявленного шелла запуск отвергается с внятным сообщением;
- `uri` — `vscode.env.openExternal`; подстановки рендерятся с целевым контекстом `uri`
  (процентное кодирование), а не конкатенируются;
- `command` — вызов произвольной команды VS Code. **Аргументы тоже проходят рендер:** подстановка в
  `args` — такой же недоверенный ввод, и ревизия 2 этот вид из контракта упускала.

Граничные случаи: команда не найдена в PATH (внятная ошибка, не молчание); процесс упал сразу; путь
с пробелами, кавычками, `;`, backtick, `%…%`, юникодом; `\n` в имени каталога; `.cmd`-цель без
объявленного шелла; действие применимо, но проект уже удалён; `primaryAction` ссылается на
несуществующий id (валидация этапа 02 не даёт этому дойти до рантайма, но исполнитель обязан пережить
рассинхрон).

Отдельное признание: `openFolder` с `window: 'current'` перезагружает окно и убивает extension host.
Незавершённые операции не переживают перезагрузку — состояние, которое должно уцелеть, не держится в
памяти.

DoD: каждый вид действия проверен вручную на живой машине; каталог с именем, содержащим `;` и
пробел, даёт в терминале корректно квотированную команду, которая **не исполнена** до нажатия Enter;
`execute: true` требует явного включения в действии.

## Пакет 04-B. Настройки, их scope и доверие

Файлы: вклады `configuration` в `package.json`, `src/editor/configuration/{settings.ts,rulesFile.ts}`.

Сведённый список настроек и их scope — **весь**, чтобы scope назначался осознанно, а не одному
пункту из шести:

| настройка | тип | scope | почему |
|---|---|---|---|
| `projectsTree.roots` | array | `machine` | направляет обход по диску; переопределение из чужого воркспейса — чтение произвольных каталогов |
| `projectsTree.maxDepth` | number | `machine` | ограничитель стоимости обхода |
| `projectsTree.location` | enum | `window` | чисто визуальная, безопасна для воркспейса |
| `projectsTree.defaultAction` | string | `machine` | ссылается на действие, то есть на исполнение |
| `projectsTree.favicon.*` | | `machine` | этап 07 |

Правила и действия в настройках **не живут вовсе** — они в отдельном файле правил
([00-overview.md](00-overview.md)): чужой репозиторий не может ни подсунуть команду, ни скомпилировать
регулярку с катастрофическим бэктрекингом в extension host.

Два разных гейта, которые прежняя ревизия смешивала:
- **доверие окна** (Workspace Trust) — объявлено в манифесте на этапе 01 как ограниченная
  поддержка; в недоверенном окне дерево работает, действия с исполнением (`terminal`, `process`)
  недоступны;
- **источник настройки** (`scope`) — таблица выше.

**Ветка, которой не было в модели угроз до round 03:** `scope: machine` означает «только user
settings **или remote settings**» (факт 18) — прошлая ревизия читала это как «только user». Значит
в remote-сценарии (SSH, dev container, WSL) `roots`, `maxDepth` и дефолтное действие приходят из
настроек удалённой машины, которую пользователь мог не настраивать сам. Требование: действия с
исполнением в remote-окне подчиняются тому же гейту доверия, что и в недоверенном воркспейсе, а
источник значения (`ConfigurationTarget`) при расхождении показывается пользователю. Проверяется
вручную в remote-окне; автоматизировать это в первом релизе не будем.

DoD: попытка переопределить `roots` в workspace-настройках игнорируется; в недоверенном окне дерево
показывается, а `terminal`/`process` не запускаются и объясняют почему.

## Пакет 04-C. Подключение к UI

Файлы: `package.json` (`commands`, `menus`, `keybindings` — на **оба** id view, см. 03-C),
`src/editor/commands/{register.ts,actionPicker.ts}`.

- клик по узлу-проекту → `projectsTree.runPrimaryAction`: берёт поле `primaryAction` вердикта,
  иначе дефолт из настроек;
- фиксированные пункты контекстного меню: «Open in New Window», «Open in Current Window»,
  «Actions…», «Hide», «Remove Root»;
- «Actions…» → QuickPick из действий, чей `appliesTo` подходит узлу. Это обход ограничения
  платформы: динамически добавить пункты в меню невозможно (факт 20);
- `projectsTree.runAction` принимает id действия аргументом — на неё можно назначить свой
  keybinding, и любимое действие получает горячую клавишу без пункта в меню.

DoD: клик открывает проект согласно настройке; «Actions…» показывает только применимые действия;
keybinding на конкретное действие работает; все пункты меню видны в обоих режимах размещения.

## Пакет 04-D. Быстрый выбор проекта

Файлы: `src/editor/commands/quickOpen.ts`.

- команда «Open Project…» — QuickPick с fuzzy-поиском по проектам; единственный способ работы в
  режиме размещения `none`;
- **в первом релизе список строится обходом по требованию**, с прогрессом и отменой (порт отмены —
  02-C, а не этап 07: он нужен уже здесь). Фонового полного обхода нет, поэтому первый вызов на
  большом дереве занимает время — честная цена отсутствия кэша;
- результат переиспользуется в пределах сессии, но **инвалидируется** при смене правил, корней или
  `maxDepth` — иначе это кэш без инвалидации, то есть ровно то, что вынесено в этап 07. Инвалидация
  общая с `NodeRegistry` (03-A).

DoD: QuickPick находит проект по частичному имени; отмена во время сбора списка прекращает чтение
ФС (счётчик вызовов порта); правка файла правил сбрасывает список; в режиме `none` команда —
достаточный способ пользоваться расширением.

## Пакет 04-E. Управление корнями и скрытием

Файлы: `src/editor/commands/{roots.ts,hidden.ts}`.

- «Add Root…» — диалог выбора папки, запись в настройки;
- «Remove Root» — удаление с подтверждением;
- «Hide» — дописывает в начало файла правил правило с условием **`pathEquals`**, а не регуляркой:
  путь может содержать метасимволы regex, и прежняя формулировка («правило `skip` по пути») их не
  экранировала;
- перед записью проверяется, не скрыт ли узел уже правилом выше — иначе создаётся мёртвое правило;
- «Manage Hidden…» — список правил, созданных скрытием, с возможностью убрать.

DoD: скрытый узел исчезает без Reload; путь с `(` и `+` скрывается корректно; повторное скрытие
уже скрытого узла сообщает об этом; «Manage Hidden» возвращает узел.

## Тестовый план этапа

Unit: выбор основного действия (поле вердикта → настройка → дефолт); фильтрация по `appliesTo`;
рендер под каждый поддерживаемый шелл и под `uri`; отклонение `\n`; сборка аргументов `process` для
путей со спецсимволами; отказ запускать `.cmd` без объявленного шелла.
Интеграционные: регистрация команд на оба view; «Hide» меняет файл правил и дерево; «Add Root» пишет
корректный путь; недоверенное окно блокирует исполняющие действия.
Ручные: все пять видов действий на живой машине, включая OpenCode в терминале и открытие в PhpStorm;
каталог с `;` в имени.
