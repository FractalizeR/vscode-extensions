# ProjectsTree — обзор плана

Ревизия 4, после трёх раундов ревью ([round 01](review-01/REPORT.md), [round 02](review-02/REPORT.md),
[round 03](review-03/findings/claude.md) — целевая проверка [api-facts.md](api-facts.md)).
Изменения ревизии: first-match применяется к полю вердикта, а не к группе полей (понятие «ось»
убрано); `descend` стал стратегией получения детей, а не сахаром над правилами; отмена переехала в
первый релиз; команда в терминал по умолчанию не исполняется; [api-facts.md](api-facts.md) требует
дословных цитат.

## Цель

Расширение VS Code, показывающее дерево проектов, найденных обходом одного или нескольких корневых
каталогов на диске, с открытием проекта одним кликом. Отличия от прототипа
(skttl/vsc-project-lobby, поверхность выписана в [prototype-surface.md](prototype-surface.md)):

1. «Что такое узел» задаётся **правилами**, а не захардкожено на `.git`;
2. узлы можно **выделять** (важные корневые папки);
3. **действия** над проектом настраиваются, включая запуск команд в терминале;
4. **онбординг** объясняет модель работы и помогает выбрать корни;
5. **редактор правил** с превью вместо ручной правки файла;
6. многоязычный интерфейс (en + ru).

Репозиторий — монорепо под несколько расширений; ProjectsTree первое из них.

## Архитектурное решение

```
Правила (classification)  ──┐
                            ├──> Дерево узлов ──> Адаптер VS Code ──> TreeView / декорации / меню
Обход (discovery)         ──┘                          │
                                                       └──> Действия (actions) ──> окно / терминал / процесс
```

**Ядро не импортирует `vscode`.** Обход, правила и модель действий — чистый TypeScript, тестируемый
без запуска редактора. Адаптер редактора живёт за этой границей и меняется по причинам платформы, а
не предмета. Граница контролируется машинно: импорт `vscode` из ядра — ошибка сборки, и правило
проверяется негативной фикстурой в CI, а не разово руками.

```
packages/projects-tree/src/
  extension.ts             — точка входа: сборка графа объектов, регистрация вкладов
  projects/                — ядро, предмет «проекты на диске»
    classification/        — условия, вердикт, движок правил
    discovery/             — обход ФС, отмена, стратегии получения детей
    actions/               — модель действий, рендер и квотирование
  editor/                  — адаптер VS Code (delivery)
    tree-view/  decorations/  commands/  onboarding/  rules-editor/
```

`projects/` — навигационная таксономия над тремя подпредметами; production-типы лежат в
подпредметах. Контракт «узел дерева» принадлежит `classification/`, `discovery/` от него зависит,
обратной зависимости нет. `HighlightSpec` живёт в `classification/`: он часть вердикта, а не деталь
отрисовки.

## Ключевая модель данных

```ts
type Condition =
  | { kind: 'nameMatches'; pattern: string; flags?: string }
  | { kind: 'hasChild'; names: string[]; entryType?: 'file' | 'dir' | 'any' }
  | { kind: 'depth'; min?: number; max?: number }
  | { kind: 'pathMatches'; glob: string; anchor?: 'root' | 'absolute' }
  | { kind: 'pathEquals'; path: string }
  | { kind: 'inRoot'; rootId: string }
  | { kind: 'all' | 'any' | 'not'; of: Condition[] }

interface Rule { id: string; title?: string; when: Condition; verdict: PartialVerdict; enabled?: boolean }
// в пользовательском файле правил ключ называется `then`; маппинг делает загрузчик (02-B).
// Внутри он `verdict`: объект с полем `then` — thenable, и `await` над одним правилом сломается.
```

**First-match применяется к каждому полю вердикта независимо.** Поля: `skip`, `stopDescend`,
`project`, `primaryAction`, `highlight`, `tags`; у каждого — своё правило-источник (`byRule`).

Это результат двух исправлений. Round 01 нашёл, что единый вердикт делал выделение и проектность
взаимоисключающими. Ревизия 2 сгруппировала поля в три «оси» — и round 02 показал, что дефект
воспроизводится внутри группы (`skip` отменял `stopDescend`, `highlight` отменял `tags`). Поле —
правильная гранулярность, и она же убирает лишнюю сущность.

Нормализация несовместимых значений задана явно: `skip: true` делает остальные поля незначимыми;
`stopDescend` значим только при `skip: false`; `primaryAction` — только при `project: true`.

Приоритет правил внутри поля — то, что выражает кейс «папка начинается с точки, но внутри `.git`»:
для поля `skip` правило про репозитории стоит выше правила про скрытые папки.

## Корень — контейнер, а не узел

Найдено проверкой на реальных данных: в `~/PhpstormProjects` пользователя лежит `.idea` (PhpStorm
держит там проект-контейнер), дефолтное правило `repo-marker` объявило корень проектом со
`stopDescend: true`, и всё дерево выродилось в один узел. 306 тестов этого не показали — в
фикстурах корень маркеров не носил.

**Решение: корень не классифицируется и не является узлом дерева.** Обход возвращает содержимое
корня; правила применяются к детям и глубже. Отвергнуты два варианта: «`stopDescend` не действует
на глубине 0» (заводит в модель исключение по глубине, зашитое в код, и всплывает на вложенных
корнях, где у второго корня своя глубина 0; плюс оставляет корень узлом-проектом, клик по которому
открывает папку со всеми проектами разом) и «правило в дефолтах, снимающее `stopDescend` на нуле»
(заплатка, требующая от пользователя понимать, почему дерево не работает).

**Корней несколько — группировка решается в UI, не в ядре.** У каждого узла есть `rootId`, поэтому
ядро одинаково отдаёт содержимое любого числа корней. Адаптер показывает: один корень — его
содержимое сразу, без промежуточного узла; несколько — каждый корень становится группирующим узлом
с меткой (контейнер: не проект, кликом не открывается). Поведение управляется настройкой
`projectsTree.showRootNodes` (`auto` — описанное, `always`, `never`), чтобы не выглядеть магией.
Корень задаётся строкой или объектом `{ path, label? }`.

## Корни и обход внутрь проектов

```ts
interface RootConfig { id: string; path: string; label?: string; descend: 'stop' | 'submodules' }
```

`descend` отвечает на вопрос «откуда брать детей проекта» и разрешает конфликт требований 2 и 5
(«прекращать обход на проекте» против «сабмодули — тоже узлы»):

- `stop` (дефолт) — проект лист;
- `submodules` — дети берутся из `.gitmodules` проекта. Один файл вместо обхода дерева: `vendor`,
  `node_modules`, `.git` не читаются вовсе.

**Это стратегия обхода, а не сахар над правилами.** Ревизия 2 объявляла `descend` разворачиваемым в
правила; round 02 показал невыразимость: `submodules` требует другого **источника детей**, а не
другого вердикта. Второго механизма остановки при этом не появляется — вопросы разные: правила
отвечают «останавливаться ли» (`stopDescend`), стратегия — «откуда брать детей, если не
останавливаемся».

Режим `full` (честный обход внутрь проекта) из первого релиза исключён: `submodules` покрывает
заявленный кейс дешевле. Условие возврата — монорепозитории, где подпроекты не сабмодули.

## Хранение правил

Правила и действия живут в файле `projects-tree.rules.json` в глобальном хранилище, а не в
`settings.json`:

- рекурсивный `Condition` требует `$ref`, а схема настройки обязана быть инлайн и `$ref` не
  поддерживает (факт 16) — полной схемы в `settings.json` не будет никогда;
- `jsonValidation` даёт файлу схему с рекурсией, то есть автодополнение ещё до визуального
  редактора (факт 17);
- файл в глобальном хранилище не переопределяется из `.vscode/settings.json` чужого репозитория.

Цена, названная явно: **файл не синхронизируется** между машинами через Settings Sync — даётся
экспорт/импорт, и это записано в README как ограничение. `fileMatch` в `jsonValidation` — шаблон
имени, а не путь, поэтому схема наведётся и на одноимённый файл в чужом проекте; риск принят
(схема ничего не исполняет). Единственный писатель файла — расширение; писатели внутри него
(редактор, «Hide», визард) сериализуются через проверку `mtime`.

В `settings.json` остаются простые настройки: корни, глубина, размещение view, дефолтное действие.

## Сквозные решения

**Совместимость.** `engines.vscode` = `^1.85.0`, proposed API не используется. Проверка в Cursor —
в этапе 01 на собранной заглушке, а не в конце.

**Ограничения платформы** (номера фактов — из [api-facts.md](api-facts.md)):

- метка выделяется через `TreeItemLabel.highlights` (1); канал общий с подсветкой встроенного
  поиска (3), поэтому цена ложится на поиск, а не на наше выделение. Настоящий bold закрыт
  proposed API (2);
- `FileDecorationProvider` глобален (8): декорации видны и в Explorer, бейдж делит место с git, а
  пользователь может выключить их настройками Explorer. `badge` — **не более двух символов**, иначе
  валидация бросает исключение и декорация отбрасывается целиком вместе с цветом (7); пустая
  декорация запрещена там же;
- поэтому выделение не строится ни на одном носителе как на единственном, и онбординг не обещает,
  что оно видно всегда;
- `propagate` распространяет декорацию к предкам, не к содержимому (9);
- контекстное меню нельзя наполнить из настроек (20, вывод): кастомные действия — через «Actions…» →
  QuickPick и keybinding на команду с аргументом;
- режимов размещения два, и это **два view с разными id** (5), с дублированием `viewsWelcome`,
  `menus`, `activationEvents` и раздельным состоянием раскрытия. `when` смотрит на собственный
  булев context key, выставляемый через `setContext`, а не на `config.` от строковой настройки:
  `config.` документирован для настроек, вычисляемых в boolean (6);
- `TreeDataProvider` адресует элементы по идентичности объекта (4), поэтому адаптер держит
  канонический элемент на ключ `rootId` + путь — не на путь: корни могут перекрываться;
- открытие в текущем окне убивает extension host (10): состояние, которое должно уцелеть, в памяти
  не держится.

**Модель угроз.** Расширение обходит чужие склонированные репозитории, поэтому недоверенных
источников два:

- *настройки воркспейса* — `roots`, `maxDepth` и дефолтное действие объявляются со `scope: machine`
  (18), правила живут вне настроек. Иначе чужой `.vscode/settings.json` направляет обход в
  произвольные каталоги. `machine` при этом означает «user **или remote** settings», поэтому в
  remote-сценарии значения приходят с удалённой машины — отдельная ветка, разобранная в 04-B;
- *данные с диска* — имена каталогов попадают в подстановки и оттуда в shell. Три меры вместо одного
  квотирования: команда в терминал по умолчанию **вставляется, но не исполняется** (11); шелл
  задаётся действием и передаётся в `shellPath` (12), а не угадывается; квотируется каждое
  подставляемое значение в момент подстановки, с учётом целевого контекста (shell, URI, литерал).
  Перевод строки в значении отвергается всегда.

Защита от дорогих регулярок — проверка сложности при валидации, **не** бюджет времени: синхронный
`RegExp` в Node прервать нечем. Остаточный риск назван; условие пересмотра — импорт правил из
внешнего источника.

`capabilities.untrustedWorkspaces` объявляется в этапе 01: без него расширение отключается целиком
в Restricted Mode (15) — то есть исчезает ровно тогда, когда пользователь открыл непроверенный клон.

**Язык.** Код, коммиты, идентификаторы, документация — английский. UI — `package.nls.json` плюс поле
`l10n` в манифесте с бандлами (19).
