## Пакет 02-A. Условия и вердикт

Файлы: `src/projects/classification/{condition.ts,rule.ts,verdict.ts,highlight.ts,classifier.ts,index.ts}`.

```ts
interface NodeFacts {
  rootId: string
  absolutePath: string
  pathFromRoot: string                // всегда '/', независимо от платформы
  name: string
  depthFromRoot: number               // 0 = сам корень
  entries: ReadonlyArray<DirEntry>
}

interface Verdict {
  skip: FieldVerdict<boolean>
  stopDescend: FieldVerdict<boolean>
  project: FieldVerdict<boolean>
  primaryAction: FieldVerdict<string | undefined>
  highlight: FieldVerdict<HighlightSpec | undefined>
  tags: FieldVerdict<readonly string[]>
}

interface FieldVerdict<T> { value: T; byRule: string | undefined }
```

Решения:

- **first-match по каждому полю независимо.** Ревизия 2 группировала поля в три «оси» и это
  воспроизводило исходный дефект внутри группы: правило, задающее `skip`, отменяло правило,
  задающее `stopDescend`; правило с `highlight` отменяло правило с `tags`. Поле — правильная
  гранулярность, и она же убирает лишнюю сущность;
- `byRule` на каждое поле — источник вердикта. Нужен превью в редакторе (этап 06) и ответу на
  вопрос «почему узел такой»;
- **нормализация несовместимых значений** определена явно, а не оставлена реализации:
  `skip: true` делает остальные поля незначимыми (узла нет в дереве); `stopDescend` значим только
  при `skip: false`; `primaryAction` значим только при `project: true`;
- `tags` — не оформление: он попадает в `contextValue` и влияет на состав контекстного меню
  (этап 04). В ревизии 2 он лежал в «оформлении», из-за чего изменение внешнего вида молча меняло
  меню;
- `rootId` в фактах: без него правило нельзя ограничить корнем, а `pathMatches` не имеет якоря;
- **проверка сложности регулярки при валидации** вместо бюджета времени. Синхронный `RegExp` в
  Node прервать нечем — ни таймером, ни токеном отмены; «бюджет времени» ревизии 2 был невыполним.
  Валидация отвергает вложенные кванторы и обратные ссылки — конструкции, дающие катастрофический
  бэктрекинг. Остаточный риск называется прямо: проверка эвристическая, гарантии линейности она не
  даёт. Условие пересмотра — появление импорта правил из внешнего источника: тогда нужен движок с
  линейной гарантией, а не эвристика;
- `Condition` остаётся закрытым union. Условие пересмотра названо значением, а не обещанием:
  второй потребитель условий помимо правил и `appliesTo` действий.

```ts
interface HighlightSpec {
  labelHighlight?: boolean   // TreeItemLabel.highlights (факт 1); занимает канал подсветки поиска (факт 3)
  color?: string             // id ThemeColor
  badge?: string             // не более двух символов, иначе декорация отбрасывается целиком (факт 7)
  icon?: string
  description?: string
  sortWeight?: number
}
```

Граничные случаи: пустая директория; нет прав на чтение; симлинк, в том числе циклический; имя со
спецсимволами regex; `depth` корня (= 0); ни одно правило не высказалось о поле (действует дефолт
поля); `badge` длиннее двух символов (валидация отвергает — иначе теряется и цвет);
`HighlightSpec` только с `sortWeight` (декорация не создаётся: пустая декорация запрещена, факт 7);
регистр имён на case-insensitive ФС macOS.

DoD: движок покрыт unit-тестами; каждый граничный случай имеет тест; отдельный тест на независимость
полей — узел, попадающий под правило выделения и правило проектности, получает оба вердикта; тест на
нормализацию — `skip: true` обнуляет значимость остальных полей.

## Пакет 02-B. Файл правил, схема и валидация

Файлы: `src/projects/classification/{validation.ts,defaults.ts,rulesFile.ts,regexSafety.ts}`,
`packages/projects-tree/schemas/rules.schema.json`.

- правила хранятся в файле `projects-tree.rules.json` в глобальном хранилище (обоснование —
  [00-overview.md](00-overview.md), факты 16–18). Имя характерное: `fileMatch` в `jsonValidation` —
  шаблон имени или глоб по пути, но абсолютный путь там невыразим (факт 17), поэтому схема наведётся
  и на одноимённый файл в чужом проекте. Риск принимается явно: схема ничего не исполняет;
- **вклад `contributes.jsonValidation` объявляется этим этапом**, вместе с самим файлом схемы: в
  этапе 01 он был бы ссылкой на несуществующий файл — `vsce package` такую ссылку пропускает, и
  установленное расширение зарегистрировало бы битую схему. Файл схемы обязан попасть в `.vsix`,
  поэтому allowlist состава пакета (01-E) расширяется этим же пакетом работ;
- **единственный писатель файла — расширение.** Внешняя правка обнаруживается по `mtime` при
  загрузке и требует перезагрузки правил; редактор (этап 06) отказывается писать поверх файла,
  изменившегося после чтения. Без этого правила «Hide», визард и редактор — три писателя, теряющие
  правки друг друга;
- валидация возвращает **все** диагностики, а не первую;
- валидируются ссылки: `primaryAction` → существующий `ActionDefinition.id`;
- версия формата файла; неизвестная версия — отказ с диагностикой;
- **синхронизации между машинами нет.** Файл в глобальном хранилище Settings Sync не переносит.
  Даётся экспорт/импорт файла, и это записывается в README как известное ограничение, а не
  умалчивается;
- дефолтный набор: проект = папка с маркером `.git` **любого типа** (у сабмодуля `.git` — файл, а
  не каталог, и маркер-только-каталог его не увидел бы) или `.idea`; `skip` для мусорных папок из
  таблицы прототипа; `skip` для скрытых папок **строго ниже** правила, оставляющего видимыми
  репозитории.

DoD: дефолтная конфигурация проходит валидацию; конфигурация с несколькими ошибками даёт все
диагностики; ссылка на несуществующее действие — диагностика; регулярка с вложенным квантором
отвергается; тест «скрытая папка с `.git` внутри — узел и проект»; тест «сабмодуль, у которого
`.git` — файл, распознан как проект»; запись поверх изменённого извне файла отвергается.

## Пакет 02-C. Отмена и поколения

Файлы: `src/projects/discovery/{cancellation.ts,generation.ts}`.

```ts
interface CancellationSignal { readonly cancelled: boolean; throwIfCancelled(): void }
```

Переехало из этапа 07: отмена нужна **первому** релизу — сбор списка для быстрого выбора проекта
(04-D) и эвристика поиска корней в визарде (05-C) обязаны прерываться. В ревизии 2 эти пакеты

- у обхода есть номер поколения; результат устаревшего поколения отбрасывается целиком, а не
  применяется частично.

DoD: отменённый обход прекращает читать ФС (по счётчику вызовов порта); результат устаревшего
поколения не попадает в дерево.

## Пакет 02-D. Обход файловой системы

Файлы: `src/projects/discovery/{walker.ts,fileSystem.ts,tree.ts,index.ts}`.

```ts
interface DirEntry {
  name: string
  type: 'file' | 'dir' | 'symlink' | 'other'
  symlinkTarget?: { type: 'file' | 'dir' | 'broken'; deviceAndInode?: string }
}

interface FileSystemReader {
  readDirectory(path: string): Promise<ReadonlyArray<DirEntry>>
  readFile(path: string, maxBytes: number): Promise<string>   // нужен для .gitmodules
  identity(path: string): Promise<string>                     // device+inode, защита от циклов
}
```

- порт отдаёт тип записи, идентичность и **чтение файла**. Последнего в ревизии 2 не было, из-за
  чего `readSubmodulePaths` из того же этапа был нереализуем; `maxBytes` — защита от гигантского
  файла на месте `.gitmodules`;
- обход ленивый; полного обхода в первом релизе нет;
- `expand` читает содержимое узла и содержимое тех детей, чьи применимые правила содержат
  `hasChild`. Условия по имени и глубине вычисляются до чтения ребёнка, поэтому `skip` по имени
  (`node_modules`) чтения не вызывает;
- конкурентность ограничена пулом;
- `maxDepth` считается от корня, **дефолт 4** (как в прототипе), `0` = только корень; `maxDepth` и
  `stopDescend` — независимые ограничители, срабатывает любой;
- симлинки по умолчанию не разыменовываются; при включённом разыменовании посещённые device+inode
  запоминаются.

Граничные случаи: несуществующий корень; корень-файл; корень без прав; **корень, вложенный в другой
корень** (узлы различаются по `rootId` + путь, а не по пути: иначе элементы двух корней
сталкиваются); сотни проектов в каталоге; папку удалили между чтением и открытием; битый симлинк.

DoD: обход тестового дерева на фейковой ФС даёт ожидаемый набор узлов; несуществующий корень —
диагностика, не падение; циклический симлинк завершается; `skip`-по-имени не читает содержимое
(счётчик); два перекрывающихся корня дают различимые узлы.

## Пакет 02-E. Стратегия получения детей проекта

Файлы: `src/projects/discovery/{descend.ts,gitmodules.ts}`.

```ts
type DescendStrategy = 'stop' | 'submodules'
interface RootConfig { id: string; path: string; label?: string; descend: DescendStrategy }

function childrenOfProject(node: ClassifiedNode, strategy: DescendStrategy): Promise<readonly ClassifiedNode[]>
function parseGitmodules(content: string): readonly { name: string; path: string }[]
```

**Это стратегия обхода, а не сахар над правилами.** Ревизия 2 объявляла `descend` разворачиваемым в
правила; round 02 показал, что это невыразимо: `submodules` требует **другого источника детей**
(список из файла), а не другого вердикта. Второго механизма остановки при этом не появляется, потому
что вопросы разные: правила отвечают «останавливаться ли» (`stopDescend`), стратегия — «откуда брать
детей, если не останавливаемся».

- `stop` (дефолт) — проект лист;
- `submodules` — дети берутся из `.gitmodules` проекта. Один файл вместо обхода: `vendor`,
  `node_modules`, `.git` не читаются вовсе;
- режим `full` (честный обход внутрь проекта) **из первого релиза исключён**: `submodules` покрывает
  заявленный кейс дешевле, а `full` требует всех ограничителей стоимости сразу. Условие возврата —
  запрос на монорепозитории, где подпроекты не сабмодули.

Разбор `.gitmodules` — контракт, а не догадка. Файл имеет git-config-грамматику:
секции `[submodule "name"]`, ключ `path`, возможны продолжения строк, кавычки, комментарии (`#`,
`;`), имена с пробелами и точками. Случаи: файла нет (проект — лист, без ошибки); файл битый
(диагностика, проект — лист); объявленный сабмодуль не инициализирован — каталога нет (узел не
показывается); путь многосегментный (`libs/vendor/foo` — узлы промежуточных каталогов создаются);
путь выходит за пределы проекта (`../x` — отвергается); вложенный сабмодуль внутри сабмодуля
(та же стратегия рекурсивно, ограничена `maxDepth`); `git worktree`, где `.git` — файл-указатель
(маркер это уже учитывает, см. 02-B).

DoD: `stop` и `submodules` дают ожидаемое дерево на фейковой ФС; `submodules` не читает ни одного
каталога внутри проекта (счётчик вызовов порта); каждый случай разбора `.gitmodules` из списка выше
имеет тест; путь с `../` отвергается.

## Пакет 02-F. Модель действий

Файлы: `src/projects/actions/{action.ts,render.ts,quoting.ts,index.ts}`.

```ts
type ActionSpec =
  | { kind: 'openFolder'; window: 'current' | 'new' | 'auto' }
  | { kind: 'terminal'; command: string; shell: ShellKind; execute?: boolean
      cwd?: string; terminalName?: string }
  | { kind: 'process'; command: string; args: readonly string[] }
  | { kind: 'uri'; template: string }
  | { kind: 'command'; commandId: string; args?: readonly unknown[] }

type RenderTarget = { kind: 'shell'; shell: ShellKind } | { kind: 'uri' } | { kind: 'literal' }
function render(template: string, node: ClassifiedNode, target: RenderTarget): string
```

- **квотируется каждое подставляемое значение в момент подстановки**, а не готовая строка.
  Ревизия 2 возвращала недоверенной всю строку, из-за чего квотировать приходилось результат
  целиком — вместе с литеральными частями шаблона, которые пользователь написал сам и которые
  квотирование ломает (`cd /x && opencode` превратилось бы в один аргумент);
- `render` знает целевой контекст: shell-квотирование, URI-кодирование или литерал. Ни одного пути,
  где подстановка попадает в sink без обработки, — включая виды `uri` и `command`, которые
  ревизия 2 из контракта упустила;
- `shell` в `ActionSpec.terminal` **обязателен**: терминал создаётся с этим `shellPath` (факт 12),
  поэтому правило квотирования известно, а не угадано по настройкам пользователя. Ревизия 2
  определяла шелл по `terminal.integrated.defaultProfile` — недостоверно;
- `execute` по умолчанию **false**: команда вставляется в терминал, но не исполняется (факт 11,
  `shouldExecute`). Пользователь видит подставленный путь и нажимает Enter сам. Это снимает главную
  тяжесть инъекции: имя каталога со спецсимволами не превращается в исполнение без ведома
  пользователя. `execute: true` — осознанный выбор пользователя для конкретного действия;
- перевод строки в подставляемом значении отвергается независимо от квотирования и от `execute`;
- переиспользование уже открытого терминала убрано: отправка в чужой шелл ломает предположение о
  правилах квотирования;
- `appliesTo` — то же `Condition`, что в правилах;
- подстановки: `${path}`, `${name}`, `${parentPath}`, `${workspaceFile}`, `${rootPath}`.

Граничные случаи: неизвестная переменная (диагностика, не пустая строка); путь с пробелами,
кавычками, `;`, backtick, `$(…)`, `%…%`, `\n`, юникодом; отсутствующий `${workspaceFile}`;
квотирование под zsh, bash, PowerShell, cmd.

DoD: по тесту на каждый спецсимвол × каждый поддерживаемый шелл; тест «литеральная часть шаблона не
квотируется»; тест «значение с `\n` отвергается»; тест «подстановка в `uri` кодируется, а не
конкатенируется».

## Тестовый план этапа

vitest, без редактора. Покрываем: условия (по тесту на вид и на комбинаторы); независимость полей;
нормализацию; проверку сложности регулярок; валидацию, включая ссылки и версию формата; отмену и
поколения; обход на фейковой ФС, включая симлинки, перекрывающиеся корни и счётчик чтений; разбор
`.gitmodules` по списку случаев; рендер и квотирование по матрице «спецсимвол × шелл».

Регрессионные тесты с обязательным docstring:
- «скрытая папка, являющаяся репозиторием» — причина приоритета правил;
- «узел под правилом выделения и правилом проектности» — причина first-match по полю;
- «сабмодуль, у которого `.git` — файл» — причина маркера любого типа;
- «имя каталога с `\n`» и «литеральная часть шаблона» — причина рендера с целевым контекстом.
