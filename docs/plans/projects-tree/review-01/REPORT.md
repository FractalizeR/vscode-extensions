## Группировка по механизму

Точечные правки применяются только там, где механизм единичен. Ниже — пять способов реализации,
каждый из которых породил несколько дефектов; для них меняется способ, а не формулировка.

### M1. Утверждения об API зафиксированы по памяти и объявлены окончательными решениями

Порождённые дефекты: перевёрнутый `propagate`; «bold недостижим» без упоминания
`TreeItemLabel.highlights`; ложный «лимит API» у `badge`; «объявляем view дважды» без цены приёма;
`refresh` по объекту; дефолт Workspace Trust; внешняя схема для `configuration`; `secrets` в
`jobs.if`; отсутствие поля `l10n` в манифесте.

Общая причина: план формулировал ограничение платформы как решение, не приложив источник. Ошибка
не в отдельных фактах — в отсутствии обязательства их подтверждать.

**Решение:** в план вводится `api-facts.md` — таблица «утверждение → источник (файл `vscode.d.ts` /
исходник / документация) → дата проверки». Ни одно решение плана не опирается на утверждение об
API, отсутствующее в этой таблице. Все девять фактов выше переписываются по источникам.

### M2. Модель угроз названа для одного источника данных

Порождённые дефекты: инъекция через `terminal` (подстановка имени каталога с диска в shell-строку);
ReDoS через регулярки из чужого `.vscode/settings.json`; перенаправление обхода через `roots` из
воркспейса; `scope` не назначен остальным настройкам.

Общая причина: `scope: machine` защищал шаблон команды, а недоверенными данными считались только
настройки. Данные с диска (имена каталогов в чужих клонах) и остальные настройки в модель не входили.

**Решение (одно на все четыре):** правила и действия переезжают из `settings.json` в отдельный файл
правил в глобальном хранилище расширения. Чужой репозиторий переопределить его не может — вектор
исчезает вместе с обсуждением `scope` для правил. Плюс явная граница доверия в ядре: результат
`substitute()` типизируется как недоверенное значение, а `terminal` получает контракт квотирования
и жёсткий запрет `\n`; `roots` и `maxDepth` объявляются со `scope: machine`.

Побочная выгода: отдельный файл снимает и ограничение `$ref` (см. M1) — рекурсивный `Condition`
описывается полной схемой через `jsonValidation`.

### M3. Вердикт как одна ось при трёх независимых

Порождённые дефекты: правило, выделяющее узел, отменяет правило, делающее его проектом (узел на
`depth: 1`, который сам является репозиторием, получает вердикт только первого правила); нет
валидации ссылки `primaryAction` → `ActionDefinition.id`.

Общая причина: `Verdict` смешал видимость/обход, проектность и оформление, а `first-match-wins`
применялся к нему целиком.

**Решение:** first-match применяется **по каждой оси независимо**. Оси: `visibility`
(`skip`/`stopDescend`), `identity` (`project` + `primaryAction`), `appearance` (`highlight`,
`tags`). Правило объявляет вердикт по одной или нескольким осям; по каждой оси решает первое
сработавшее правило. Кейс сабмодуля сохраняется (ось видимости), выделение перестаёт конфликтовать
с проектностью.

### M4. Фоновая асинхронность без контракта

Порождённые дефекты: `refresh` на пересобранном узле — no-op; DoD кэша противоречит себе
(`mtime`-проверка и есть чтение ФС); отсутствие отмены и поколений у конкурирующих обходов;
отрицательный кэш favicon без инвалидации; чем дерево узнаёт об изменениях на диске — не решено.

Общая причина: поток «показать из кэша → фоновая перепроверка → обновить» объявлен целью, но не
имеет ни контракта идентичности элементов, ни контракта отмены.

**Решение:** кэш и фоновая перепроверка **убираются из первого релиза целиком**. Ленивый обход
одного уровня быстр сам по себе, и без кэша исчезает весь класс дефектов. Возвращаются отдельным
этапом, где сразу описываются: реестр узлов по пути (канонический элемент, обновляемый на месте),
`CancellationToken` и поколение обхода, инвалидация через `FileSystemWatcher`.

### M5. Валидация объявлена полной, но собрана не целиком

Порождённые дефекты: интеграционные тесты `@vscode/test-cli` не входят ни в `check`, ни в CI;
Prettier не проверяется в `check`; правила dependency-cruiser не ловят часть заявленных границ;
webview вне workspace.

**Решение:** `check` определяется списком проверок, и каждый вводимый класс проверок обязан быть в
него добавлен в том же пакете, что его вводит. Для интеграционных тестов — отдельная джоба CI с
`xvfb` (в `check` они не идут: требуют запуска редактора).
