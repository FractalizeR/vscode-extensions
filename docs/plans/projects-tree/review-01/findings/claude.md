### claude-01

- **reviewer**: claude
- **severity**: HIGH
- **kind**: contract
- **domain**: security
- **title**: Действие `terminal` собирает shell-строку из имён каталогов — инъекция, которую план не видит
- **mechanism**: `04-A` явно защищает только `process` («аргументы передаются массивом, никогда не собираются в строку для shell»). Но `terminal` по определению склеивает строку: `ActionSpec.terminal.command` из настроек + `substitute()` подставляет `${path}`, `${name}`, `${parentPath}` и отдаёт результат в `Terminal.sendText`. Значения подстановок берутся **не из настроек, а с диска** — это имена каталогов в сканируемых корнях, то есть содержимое чужих склонированных репозиториев и сабмодулей. Имя каталога может содержать `;`, `` ` ``, `$(...)`, `&&`, кавычки и, что хуже всего, `\n`: `sendText` по умолчанию исполняет отправленный текст, а перевод строки внутри аргумента даёт вторую команду. Атрибут `scope: machine` защищает шаблон команды, но не защищает подставляемые в него данные — модель угроз в `04-B` рассматривает только источник «настройки», а не источник «файловая система».
- **trigger**: воспроизводится в нормальной работе — достаточно, чтобы в сканируемом корне оказался каталог со спецсимволом в имени (создаётся клонированием или распаковкой архива, прав не требует)
- **in_scope**: да
- **anchor**: `04-actions.md` пакет 04-A (`terminal`), пакет 04-B («Ключевое решение по безопасности»); `02-core.md` пакет 02-E (`substitute`)
- **evidence**: `04-A`: «`terminal` — `window.createTerminal({ cwd })` + `sendText`»; защита от инъекции сформулирована только для `process`: «Аргументы передаются массивом, **никогда не собираются в строку для shell** — иначе путь с пробелами или `;` становится инъекцией». Для `terminal` эквивалентной защиты в плане нет, а `02-E` описывает `substitute` как чистую текстовую подстановку без экранирования («Граничные случаи: … путь с пробелами и кавычками» — как случай форматирования, не как класс уязвимости).
- **verification**: confirmed
- **verification_note**: противоречие внутри самого плана: та же угроза названа для `process` и не рассмотрена для `terminal`, при том что `terminal` — единственный вид действия, где строка обязательно попадает в shell. Проверять кодом нечего — кода нет.
- **fix_direction**: задать в модели действий явную границу доверия: подстановки — недоверенные данные, а не текст. Для `terminal` определить контракт квотирования на стороне ядра (per-shell), либо отказаться от подстановки в строку команды и передавать путь только через `cwd` и переменные окружения терминала. Отдельно закрыть перевод строки в подставляемых значениях как жёсткий инвариант с тестом. То же правило распространить на `uri` (шаблон URI требует процентного кодирования, а не конкатенации) и зафиксировать в тестовом плане 04 как класс, а не как edge case.

### claude-02

- **reviewer**: claude
- **severity**: HIGH
- **kind**: contract
- **domain**: reliability
- **title**: `refresh(node)` на пересобранном узле — молчаливый no-op: VS Code адресует элементы по идентичности объекта
- **mechanism**: Центральный поток отрисовки в плане — «дерево отдаёт узлы из кэша сразу, фоновая перепроверка вызывает `refresh` затронутой ветки» (`03-A`), и он же в `02-D`. Но `ExtHostTreeView` хранит соответствие элемент→узел в `Map<T, TreeNode>`, то есть по ссылке на объект. Фоновая перепроверка перечитывает ФС и **классифицирует заново**, получая новые экземпляры `ClassifiedNode`; `refresh(newNode)` даст `this._nodes.get(element) === undefined`, список хендлов окажется пустым и обновление не произойдёт — без исключения и без диагностики. Такой отказ не поймается ни unit-тестами ядра (там нет `vscode`), ни объявленными интеграционными тестами 03 («регистрация view, `getChildren` на временном дереве») — он проявится как «дерево показывает устаревшее состояние из кэша».
- **trigger**: воспроизводится в нормальной работе — на каждой фоновой перепроверке после отрисовки из кэша
- **in_scope**: да
- **anchor**: `03-tree-view.md` пакет 03-A (`refresh(node?): void // частичное обновление ветки`)
- **evidence**: `src/vs/workbench/api/common/extHostTreeViews.ts:329` — `private _nodes: Map<T, TreeNode> = new Map<T, TreeNode>();`; там же `_getHandlesToRefresh` (строка ~810): `const elementNodes = elements.map(element => this._nodes.get(element));` и далее обновляются только найденные хендлы, иначе `_refresh` возвращает `Promise.resolve(undefined)` (строки 790–806).
- **verification**: confirmed
- **verification_note**: подтверждено исходником текущей ветки `main`; `TreeItem.id` стабилизирует состояние раскрытия в UI, но на сопоставление элементов в extHost не влияет — там используется сам объект.
- **fix_direction**: ввести в адаптер единый реестр узлов по пути (path → канонический элемент), возвращаемый из `getChildren`, и обновлять его содержимое на месте вместо замены объектов; либо перейти на элементы-идентификаторы (строка пути) и хранить состояние отдельно. Решение должно быть зафиксировано контрактом `TreeDataProvider` в 03-A, а не оставлено реализации, и покрыто интеграционным тестом «после фоновой перепроверки ветка перерисовалась».

### claude-03

- **reviewer**: claude
- **severity**: HIGH
- **kind**: contract
- **domain**: security
- **title**: Workspace Trust: без объявления `capabilities.untrustedWorkspaces` расширение отключается целиком, а не «только действия»
- **mechanism**: `04-B` формулирует поведение так: «действия не запускаются, если окно не доверенное (Workspace Trust)» — то есть предполагается, что дерево в недоверенном окне работает, а исполнение заблокировано. Но по умолчанию (когда в манифесте нет `capabilities.untrustedWorkspaces`) VS Code считает расширение не поддерживающим Workspace Trust и **отключает его полностью** в Restricted Mode. Ни один пакет плана не объявляет эту секцию манифеста. Итог противоположен и замыслу, и продуктовой цели: лончер проектов, который исчезает именно в тот момент, когда пользователь открыл непроверенный клон, — при этом ровно из него он и хочет уйти в другой проект. Параллельно не объявлен `capabilities.virtualWorkspaces`: ядро ходит по `node:fs`, в виртуальном воркспейсе (`vscode-vfs://`) оно неработоспособно, и это тоже должно быть заявлено манифестом, а не выясняться у пользователя.
- **trigger**: воспроизводится в нормальной работе — первое же открытие недоверенной папки
- **in_scope**: да
- **anchor**: `04-actions.md` пакет 04-B; `00-overview.md` раздел «Безопасность настроек»
- **evidence**: https://code.visualstudio.com/api/extension-guides/workspace-trust — «an extension that does not contribute anything to their `package.json` will be treated as not supporting Workspace Trust. It will be disabled when a workspace is in Restricted Mode»; поддерживаемые значения — `{supported: true}` / `{supported: false, description}` / `{supported: 'limited', description}`.
- **verification**: confirmed
- **verification_note**: подтверждено официальным руководством; план описывает намерение (`limited`), но не описывает механизм, которым это намерение выражается, а дефолт механизма противоположен намерению.
- **fix_direction**: внести объявление `capabilities.untrustedWorkspaces` со значением «ограниченная поддержка» и описанием ограничения в пакет, который первым добавляет манифестные вклады (01-D), а не в 04 — иначе с 03 по 04 расширение будет отключаться в недоверенных окнах. Там же объявить отношение к виртуальным воркспейсам. Разделить в 04-B два разных гейта: доверие окна (Workspace Trust) и источник настройки (`scope`), и в тестовом плане 05 проверить оба состояния.

### claude-04

- **reviewer**: claude
- **severity**: HIGH
- **kind**: contract
- **domain**: architecture
- **title**: Модель вердиктов сводит три независимые характеристики узла к одному «первое сработавшее решает» — комбинаторный взрыв правил и молчаливое сужение требования 4
- **mechanism**: Требование 4 называет три ортогональные характеристики: «считать ли узлом», «проект», «выделять» — каждая как отдельный критерий по данным. План выражает все три полями одного `Verdict` и добавляет правило «вердикт даёт первое сработавшее правило, остальные не смешиваются» (`02-A`). Отсюда: чтобы узел был одновременно проектом и выделенным, нужно правило, повторяющее условие проекта и добавляющее `highlight`; при N критериев выделения и M критериев «проект» пользователь обязан завести N×M правил, вручную удерживая их взаимную непротиворечивость. На заявленной структуре пользователя это ломается сразу: правило «выделять первый уровень» (`{depth: max 1}`, оно же предустановка в `05-C`) и правило «проект = папка с `.git`» пересекаются на любом репозитории, лежащем прямо в корне, — что произойдёт, зависит от порядка, и в обоих порядках пользователь теряет одну из двух характеристик. Обоснование выбора «приоритетный список вместо набора флагов» (кейс 5: скрытая папка с `.git`) требует упорядоченности только по оси видимости и не обосновывает склейку остальных двух осей.
- **trigger**: воспроизводится в нормальной работе — на структуре `roots/{домен}/{проект}` при первой же попытке выделить папку, которая сама является проектом
- **in_scope**: да
- **anchor**: `Verdict` / `Classifier` (`02-core.md` пакет 02-A, `00-overview.md` «Ключевая модель данных»)
- **evidence**: `00-overview.md`: «**Первое сработавшее правило решает.** Не набор независимых флагов… Вердикты правил ниже по списку не смешиваются»; `Verdict` содержит `project`, `stopDescend`, `skip`, `highlight`, `primaryAction`, `tags` в одной структуре. Требование 4 брифа: «Характеристика узла (проект / выделять / считать ли узлом) — это критерий по данным».
- **verification**: unverifiable
- **verification_note**: кода нет; дефект выводится из сопоставления модели с требованием и с примером структуры из самого плана (`05-C`, предустановка «выделять первый уровень»). Проверяется мысленным исполнением, не исходником.
- **fix_direction**: развести оси: приоритетный список сохранить там, где важна взаимоисключающая семантика (видимость/обход/что считать проектом), а выделение и привязку основного действия сделать отдельным проходом со своей семантикой накопления (последнее/наибольший приоритет побеждает). Либо оставить единый список, но задать явное правило композиции по каждому полю вердикта и `continue`-семантику для правил, не завершающих разбор. Что бы ни было выбрано — это должно быть решением в `02-A` с тестом на кейс «проект в корне, который надо выделить», иначе редактор правил из этапа 06 будет визуализировать модель, в которой пользователь не может выразить свою структуру.

- **severity**: HIGH
- **kind**: contract

- **title**: `scope: machine` объявлен только для действий: правила и корни из чужого `.vscode/settings.json` дают ReDoS и произвольное сканирование

(2) Подмена корней: `roots`, указанные в чужом воркспейсе, направляют фоновый полный обход (нужный для QuickPick, `03-D`) и поиск favicon в произвольные каталоги — включая сетевые монтирования и `$HOME` целиком — что даёт и зависание, и нежелательное чтение. Ни то, ни другое не требует исполнения команд, поэтому гейт «действия недоступны в недоверенном окне» здесь не помогает.
- **trigger**: воспроизводится в нормальной работе — открытие склонированного репозитория со своим `.vscode/settings.json`
- **in_scope**: да
- **anchor**: `04-actions.md` пакет 04-B; `02-core.md` пакеты 02-A, 02-B; `03-tree-view.md` пакет 03-D
- **evidence**: `04-B`: «Настройка **действий** объявляется со `scope: "machine"`» — только про действия. https://code.visualstudio.com/api/references/contribution-points#contributes.configuration: `window` — «can be configured in user, workspace, or remote settings», и это дефолтный scope; не переопределяются из воркспейса только `application` и `machine`.
- **verification**: confirmed
- **verification_note**: семантика scope подтверждена документацией; отсутствие scope у остальных настроек подтверждается тем, что план называет scope ровно один раз и ровно для действий.

### claude-06

- **reviewer**: claude
- **severity**: MEDIUM
- **kind**: contract
- **domain**: reliability
- **title**: Семантика `FileDecoration.propagate` в плане перевёрнута: распространение идёт к родителям, а не к содержимому
- **mechanism**: `03-B` содержит решение «`propagate` у декорации выключен: выделение корневой папки не должно красить всё её содержимое». Флаг работает в другую сторону: он распространяет декорацию **на предков** ресурса (так git-декорации показывают «внутри есть изменения» на родительских папках). Декорации никогда не наследуются вниз, поэтому опасность, ради устранения которой принято решение, не существует, а сам флаг — единственный доступный механизм пометить родителя, содержащего интересные узлы (что для дерева проектов как раз полезно: «в этом домене есть выделенные проекты»). Решение принято на неверно понятой семантике, то есть выключает ровно то, что могло бы понадобиться, по причине, которой нет.
- **trigger**: только в замысле — приводит к неправильно принятому решению, а не к сбою
- **in_scope**: да
- **anchor**: `03-tree-view.md` пакет 03-B (`propagate`)
- **evidence**: `src/vscode-dts/vscode.d.ts`, класс `FileDecoration`: «A flag expressing that this decoration should be propagated to its **parents**»; там же `FileDecorationProvider.onDidChangeFileDecorations`: «a decoration from a descendent that propagates upwards must be signaled to the editor».
- **verification**: confirmed
- **verification_note**: подтверждено `vscode.d.ts` ветки `main`.
- **fix_direction**: переформулировать решение: `propagate` не защищает от окрашивания содержимого (этого эффекта нет вовсе), а выбирается по вопросу «должен ли родительский узел показывать, что внутри есть выделенное». Заодно учесть, что при включении потребуется явно сигналить `onDidChangeFileDecorations` для предков.

### claude-07

- **verification**: confirmed
- **verification_note**: подтверждено `vscode.d.ts` и исходником `decorationsService.ts`; встроенное git-расширение использует тот же публичный API, поэтому попадает в то же слияние.
