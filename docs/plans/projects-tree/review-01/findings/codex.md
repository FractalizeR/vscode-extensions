## HIGH

### codex-01

- **reviewer**: codex
- **severity**: HIGH
- **kind**: contract
- **domain**: architecture
- **title**: Один `view` нельзя дважды объявить в разных контейнерах
- **mechanism**: План предлагает объявить один и тот же view в собственном activity-bar контейнере и в Explorer, переключая видимость через `when: config.projectsTree.location`. VS Code требует глобально уникальные `view id`; повторная регистрация одного id отклоняется.
- **trigger**: воспроизводится в нормальной работе — режим `explorer` (или `activityBar`) не зарегистрируется при буквальной реализации плана
- **in_scope**: да
- **anchor**: 00-overview.md, «Ограничения платформы», п.3; 03-tree-view.md, пакет 03-D
- **evidence**: Самостоятельно проверено в исходнике `viewsExtensionPoint.ts` (microsoft/vscode, ветка main): `collector.error(localize('duplicateView1', "Cannot register multiple views with same id \`{0}\`", item.id))`. `when: config.<key>` для view/menu поддерживается официально (references/when-clause-contexts) — сама идея переключения через настройку рабочая, ломается только повторное использование одного id.
- **verification**: confirmed
- **verification_note**: Проверено фасилитатором напрямую по исходнику VS Code (grep по `viewsExtensionPoint.ts`), не только со слов codex.
- **fix_direction**: Спроектировать два разных view id с общим провайдером данных (или явно оставить один view и полагаться на штатное перетаскивание пользователем между контейнерами вместо программного переключения).

### codex-02

- **reviewer**: codex
- **severity**: HIGH
- **kind**: contract
- **domain**: architecture
- **title**: `ClassifiedNode`/`NodeFacts` не хранит идентичность корня
- **mechanism**: `NodeFacts` содержит `absolutePath` и `depthFromRoot`, но не `rootId`/`rootPath`. При этом `pathMatches` матчится относительно корня, `${rootPath}` должен разрешаться из узла, а «Hide» обязан скрывать один конкретный узел. При нескольких (тем более вложенных) корнях с одинаковой относительной структурой это неоднозначно.
- **trigger**: воспроизводится в нормальной работе — два корня с похожей структурой делают `${rootPath}` и точечный Hide неоднозначными
- **in_scope**: да
- **anchor**: контракт `NodeFacts`/`ClassifiedNode` в 02-core.md, пакет 02-A; `${rootPath}` в пакете 02-E; «Hide» в пакете 04-D
- **evidence**: `substitute(template, node)` не получает корень отдельным параметром; `NodeFacts` не содержит поля, из которого корень восстанавливается однозначно, при этом план параллельно обещает multi-root, root-relative matching и `${rootPath}`.
- **verification**: confirmed
- **verification_note**: Логическое противоречие внутри самого плана (контракт vs использование), проверяется чтением, не требует внешней документации.
- **fix_direction**: Включить принадлежность корню (id или нормализованный root-relative путь) в `NodeFacts`/`ClassifiedNode`; отдельно определить поведение для вложенных/пересекающихся корней.

### codex-05

- **reviewer**: codex
- **severity**: HIGH
- **kind**: contract
- **domain**: security
- **title**: Подстановка `${path}`/`${name}`/`${workspaceFile}` в terminal-действии допускает command injection
- **mechanism**: Значения подстановки берутся из просканированной файловой системы (чужих склонированных репозиториев) и вставляются в строку, передаваемую в `Terminal.sendText`, которая исполняется шеллом пользователя без универсального экранирования. Спецсимволы шелла в имени каталога (кавычка, `$()`, `;`, перевод строки) могут изменить исполняемую команду.
- **trigger**: воспроизводится в нормальной работе — пользователь запускает настроенное terminal-действие (например, «OpenCode в терминале») на специально названном клонированном каталоге
- **in_scope**: да
- **anchor**: 02-core.md, пакет 02-E (`substitute`); 04-actions.md, пакеты 04-A/04-B
- **evidence**: `Terminal.sendText` документирован как отправка текста в stdin реального шелла (по умолчанию с исполнением); `scope: machine` в плане защищает только определение действия в настройках, но не значения, подставляемые из имён файлов/папок.
- **verification**: confirmed
- **verification_note**: `process`-действие в плане явно защищено (аргументы массивом, без сборки shell-строки, п.04-A) — то же самое свойство не распространено на `terminal`-действие, хотя источник данных (сканируемая ФС) идентичен по риску.
- **fix_direction**: Для команд, не требующих интерактивного терминала, передавать проект через `cwd`, а не interpolation в командную строку; для случаев, где interpolation неизбежна — экранировать под целевой shell или подтверждать у пользователя финальную команду перед отправкой.

### codex-06

- **reviewer**: codex
- **severity**: HIGH
- **kind**: contract
- **domain**: reliability
- **title**: `if:` по наличию секрета в publish-джобах не работает так, как описано
- **mechanism**: План описывает `publish.yml` как job'ы с `if:` по наличию `VSCE_PAT`/`OVSX_PAT`, чтобы включение публикации сводилось к добавлению секретов. GitHub Actions не позволяет напрямую ссылаться на `secrets.*` в выражении `if:` job'а.
- **trigger**: воспроизводится в штатном CI — при первом прогоне workflow (или при статическом анализе workflow-файла)
- **in_scope**: да
- **anchor**: 01-monorepo-and-tooling.md, пакет 01-E
- **evidence**: Официальная документация GitHub Actions («Using secrets in a workflow») прямо указывает, что секреты нельзя использовать непосредственно в условии `if:`.
- **verification**: confirmed
- **verification_note**: Известное и документированное ограничение GitHub Actions, не специфика проекта.
- **fix_direction**: Использовать поддерживаемый паттерн (например, секрет как `job.environment`/на уровне step с явной проверкой пустоты значения, либо отдельный non-secret флаг-переменная) вместо прямого `if: secrets.X`.

### codex-10

- **reviewer**: codex
- **severity**: MEDIUM
- **kind**: contract
- **domain**: reliability
- **title**: Порт `FileSystemReader` недостаточен для заявленной symlink/inode-политики
- **mechanism**: Порт объявляет только `readDirectory`/`statMtime`, но walker по плану должен распознавать симлинки и запоминать посещённые inode для защиты от циклов. Ни `readDirectory`, ни `statMtime` не возвращают тип записи (symlink/dir/file), inode или device — этой информации через объявленный контракт получить нельзя.
- **trigger**: воспроизводится при реализации заявленной symlink-политики — walker будет вынужден выйти за пределы порта (обратиться к `node:fs` напрямую) либо не сможет реализовать защиту от циклических симлинков и тест на неё
- **in_scope**: да
- **anchor**: 02-core.md, пакет 02-C, контракт `FileSystemReader`
- **evidence**: сигнатура порта не содержит полей, необходимых для объявленного поведения («симлинки по умолчанию не разыменовываются; посещённые inode запоминаются»), при этом «тест на циклический симлинк завершается» входит в DoD того же пакета.
- **verification**: confirmed
- **verification_note**: Несоответствие контракта и описанного поведения видно из самого текста пакета 02-C.
- **fix_direction**: Либо упростить политику до «симлинки никогда не разыменовываются» (тогда inode-tracking не нужен и удаляется из описания), либо расширить порт минимальной identity-операцией (аналог `lstat`).

- **in_scope**: да

- **evidence**: перечень команд `check` в пакете 01-B не включает шаг Prettier, хотя в том же файле ниже это поведение заявлено как DoD.
- **verification**: confirmed
- **verification_note**: Прямое внутреннее противоречие между составом команды и заявленным DoD в одном и том же документе.
- **fix_direction**: Добавить `prettier --check` в цепочку `check` (до или вместе с `lint`).

## Refuted

codex-01(исходный, technical) | «Стабильный API VS Code с версии 1.106 поддерживает `MarkdownString` в `TreeItem.label`, план ошибочно отказывается от bold» | Фасилитатор проверил напрямую по исходникам `microsoft/vscode` (ветка main, файл `src/vscode-dts/vscode.d.ts`): в стабильном API `TreeItem.label?: string \| TreeItemLabel`, а `TreeItemLabel.label: string` — plain text. Поддержка `MarkdownString` в label существует только как **proposed API** (`vscode.proposed.treeItemMarkdownLabel.d.ts`), недоступный для опубликованных Marketplace-расширений без специального allow-listing, и сам план явно исключает proposed API («proposed API не используем», 00-overview.md). Указанные в исходном ответе release notes (v1.106) описывают эту возможность именно в разделе Proposed APIs, а не Stable. Таким образом исходное утверждение плана о недостижимости bold — корректно для условий, которые план сам на себя накладывает.
codex-16 | `scope: machine` всё равно читается из `.vscode/settings.json` чужого репозитория | официальная документация `contributes.configuration` подтверждает, что `machine`-scope можно задать только на уровне User/Remote settings, не через workspace
codex-17 | `config.<key>` в принципе нельзя использовать в `when` для переключения view | механизм официально поддерживается (references/when-clause-contexts); реальная проблема — не в этом, а в уникальности `view id` (см. codex-01 в разделе HIGH)
codex-18 | Walkthrough не открывается автоматически при первой установке | `contributes.walkthroughs` официально поддерживает auto-open по умолчанию для нового расширения
codex-19 | `vscode.openFolder` не принимает объект опций | встроенная команда официально принимает `{forceNewWindow, forceReuseWindow}`
codex-20 | Динамическая регистрация команды (`projectsTree.runAction`) сама по себе создаёт динамический пункт контекстного меню | `registerCommand` не создаёт menu-contribution; выбор QuickPick как обходного пути в плане корректен
