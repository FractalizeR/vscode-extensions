## Контекст задачи

Пользователь хочет монорепо под свои расширения VS Code. Первое расширение — ProjectsTree: дерево
проектов, найденных обходом корневых каталогов на диске (у пользователя корень
`~/PhpstormProjects`, внутри `{домен}/{проект}`). Прототип для «взять лучшее» —
https://github.com/skttl/vsc-project-lobby (там проект = папка с `.git`, набор плоских настроек).

Требования пользователя дословно:
1. Расширения собираются артефактами, публикуются в релизы; автопубликация позже.
2. Проект — папка с маркерным файлом/каталогом (`.git`, `.idea`); после обнаружения обход вглубь
   прекращается.
3. Некоторые папки важные — их надо визуально выделять («выделил бы жирным»).
4. Характеристика узла (проект / выделять / считать ли узлом) — это критерий по данным: регулярка по
   имени, наличие маркерного файла внутри, позже что-то ещё.
5. Есть кейс: папка начинается с точки, но является репозиторием (сабмодули) — её надо считать узлом.
6. Основное действие — открыть в VS Code (в том же/новом окне), альтернативные действия настраиваемые
   (например, запустить OpenCode в терминале в папке проекта).
7. Нужен удобный редактор правил (не JSON руками).
8. Визард онбординга: выбрать корни и объяснить, как работает расширение.
9. Иконка на левой панели (activity bar) + менее инвазивная альтернатива, переключаемая настройкой.
10. Публикация: заложить сразу, включая Open VSX.
11. Интерфейс многоязычный (en + ru), если поддерживается.
12. Покрыть Cursor, если без серьёзного ущерба.
13. Нужны `AGENTS.md` и `CLAUDE.md` симлинком на него.
14. Репо ведётся агентом, тулинг полный и строгий: линтеры, контроль архитектуры.

## Что от вас нужно

Ревью **плана**, а не кода. Наиболее ценные классы находок, в порядке приоритета:

1. **Неверные технические факты о VS Code API.** План опирается на утверждения об ограничениях
   платформы и на них строит решения. Если утверждение ложно — решение построено на песке. Проверьте
   в частности: невозможность жирного шрифта в `TreeItem.label`; поведение
   `FileDecorationProvider` (нужен ли `resourceUri`, что даёт `badge`/`color`/`propagate`);
   невозможность динамически наполнить `contributes.menus` из настроек; работоспособность
   `when: config.<key>` для переключения видимости view между контейнерами; статус
   `@vscode/webview-ui-toolkit`; механика `package.nls.*` + `vscode.l10n`; семантика
   `scope: "machine"` у настройки; поведение `walkthroughs` и условий завершённости шагов;
   `vscode.openFolder` и его опции. Каждый факт — со ссылкой на документацию или исходники VS Code.
2. **Дефекты модели правил.** Приоритетный список правил с «первое сработавшее решает». Достаточно
   ли этого для перечисленных требований пользователя? Какие реальные структуры каталогов модель не
   выражает? Есть ли требование из списка выше, которое модель не покрывает?
3. **Ошибки декомпозиции и границ.** Раскладка `projects/` (ядро без `vscode`) против `editor/`
   (адаптер). Правильно ли лежат контракты (`Condition` в `classification/`, порт ФС в ядре)? Нет ли
   этапа, который не может быть выполнен в объявленном порядке из-за незамеченной зависимости?
4. **Пропущенные требования пользователя.** Сверьте список из 14 пунктов выше с планом поштучно;
   пропуск или молчаливое сужение требования — находка.
5. **Дыры в безопасности замысла.** Действия исполняют произвольные команды из настроек; расширение
   ходит по чужим склонированным репозиториям. Достаточна ли защита (`scope: machine`, Workspace
   Trust)? Есть ли вектор, который план не видит?
6. **Производительность замысла.** Ленивый обход, читающий на уровень глубже, чем показывает; кэш с
   инвалидацией по `mtime` каталога; фоновый полный обход для QuickPick. Где это развалится на
   реальном дереве в сотни проектов?
7. **Тулинг.** Достаточен ли набор для репозитория, который ведёт агент? Ловят ли объявленные правила
   dependency-cruiser заявленные границы? Чего в наборе не хватает критически?

Отдельно ценно: **что в плане переусложнено** и что стоит выбросить из первого релиза.
