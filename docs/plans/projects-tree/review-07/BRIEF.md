# Задание ревьюерам — round 07 (этап 04 ProjectsTree: действия)

Материал не делится на слайсы: ожидаемые дефекты — межфайловые, на швах между пакетами. Прошлые
раунды дали железную закономерность: худшее находится не внутри пакета, а между ними
(`review-05/REPORT.md` — стратегия обхода была реализована, покрыта тестами и никогда не вызывалась
из production; `review-06/REPORT.md` — правила пользователя подставлялись вместо дефолтных, чего не
показали 424 теста).

## Что ревьюируем

Незакоммиченное рабочее дерево ветки `feat/projects-tree-actions` относительно `origin/main`
(`beb38ae`). Материал снимается так:

```
git diff beb38ae -- . ':!pnpm-lock.yaml'
git status --short   # новые файлы
```

Этап 04 плана: `docs/plans/projects-tree/04-actions.md` — пять пакетов (04-A исполнители действий,
04-B настройки и доверие, 04-C подключение к UI, 04-D быстрый выбор проекта, 04-E корни и скрытие),
плюс два долга этапа 03, закрытых здесь. **В конце файла плана есть раздел «Решения, изменённые при
реализации» — читайте его**: там перечислено, где реализация сознательно отошла от текста плана и
почему. Отход, который там не назван, — находка.

Исполнителей было шесть, каждый видел только свой набор файлов. `src/extension.ts` правили три из
них по очереди.

## Обязательный контекст

1. **`AGENTS.md`** — канон репозитория: машинно проверяемые границы (`src/projects/**` не импортирует
   `vscode`), состав `pnpm check`, правило про `api-facts.md`, запрет править планы под уже
   написанный код.
2. **`docs/plans/projects-tree/api-facts.md`** — ни одно решение не имеет права опираться на
   утверждение об API, которого нет в этой таблице; строка недействительна без дословной цитаты.
   В этом раунде особенно строки 10-13, 18, 20, 25, 29, 34, 48 и новые 62-85. Новые строки добывали
   те же исполнители, что писали по ним код, — проверьте не только «есть ли строка», но и «говорит
   ли источник то, что из него вывели».
3. **`docs/plans/projects-tree/00-overview.md`**, раздел «Модель угроз» — два недоверенных источника
   (настройки воркспейса и данные с диска) и три меры против второго.
4. **`review-05/REPORT.md`** и **`review-06/REPORT.md`** — механизмы отказа прошлых раундов.
   Проверьте, не воспроизведён ли любой из них заново.

## Куда смотреть в первую очередь

Гипотезы оркестратора, а не ограничение области. Coverage фиксируйте по всему диффу.

- **Обход гейта доверия.** `ExecutionGate.check()` — единственная защита исполняющих действий
  (`terminal`, `process`, `command`). Путей запуска действия несколько: клик по узлу
  (`runPrimaryAction`), контекстное меню, `runAction` с аргументом из keybinding, «Actions…»,
  выбор в быстром выборе проекта. **Вопрос: существует ли хоть один путь, где действие исполняется,
  минуя `check()`.** Один такой путь обнуляет весь пакет 04-B.
- **Полнота квотирования на реальных стоках.** `render`/`quoteForShell` написаны на этапе 02 и
  считаются корректными. Проверять надо не их, а **вызовы**: каждое ли значение, попадающее в
  терминал, argv, URI и аргументы команды VS Code, проходит через `render` с правильным
  `RenderTarget`; нет ли места, где путь конкатенируется в строку мимо рендера (в первую очередь
  `cwd` терминала, имя терминала, аргументы `process`, шаблон `uri`).
- **Потеря пользовательских данных при записи файла правил.** `Hide` и `Manage Hidden` — первые
  писатели `projects-tree.rules.json`. Файл может содержать то, чего эти команды не создавали:
  секцию `actions`, `title`, `enabled`, правила пользователя в произвольном порядке. Проверьте
  round-trip чтение→правка→запись на сохранность всего, чего команда не трогала, и поведение при
  файле с диагностиками (нельзя молча перезаписать сломанный файл, потеряв его содержимое).
  Отдельно: два писателя подряд и проверка `mtime` — что произойдёт при записи в файл, который
  человек редактирует руками в этот же момент.
- **Швы между пакетами.** Поимённо: `src/extension.ts` (сборка графа, три автора);
  `ExecutionGate`/`ExecutionDecision` (объявлялись независимо в `configuration/trust.ts` и
  `commands/actions/runner.ts`, потом сведены — проверьте, что действительно одно объявление);
  `NodeSelection` (структурный шов между `commands/` и `tree-view/`, чтобы не было цикла);
  `ProjectsTreeProvider`'s `getMaxDepth` — **сделан опциональным** ради интеграционных тестов, то
  есть вызывающий может его молча забыть и получить дефолт 4. Вопрос тот же, что и всегда: **какую
  форму входа не покрыл ни один пакет.**
- **Вызывается ли новый код из production.** Обязательный пункт приёмки в этом репозитории: для
  каждого нового экспортируемого символа должен быть вызов вне тестов. `knip` ловит это частично.
  Обратная сторона: **работа без наблюдаемого эффекта**. В этом этапе такое находили дважды (явный
  сигнал предков в декорациях; context key `executionAllowed`, который никто не читал) — оба
  удалены. Поищите третий случай.
- **`propagate` как поле правила.** Факт 62 (добыт в этом этапе) утверждает: платформа поднимает
  декорацию по литеральной иерархии путей, границы «в пределах нашего корня» не существует, а
  сигнала по URI самого узла достаточно. Проверьте, что код и комментарии не обещают границы,
  которой нет, и что валидация не пропускает `propagate` без носителя.
- **Инвалидация кэша быстрого выбора.** Кэш живёт в композиционном корне и сбрасывается по смене
  правил, корней и `maxDepth`. Проверьте, нет ли пути, меняющего состав проектов без сброса — в
  первую очередь `Hide`/`Manage Hidden`, которые меняют правила через собственный писатель, а не
  через настройки.
- **Локализация.** 37 рантайм-строк и 27 манифестных. Проверьте совпадение плейсхолдеров (`{0}`,
  `{1}`) между английской и русской сторонами и отсутствие строк, собранных конкатенацией (такие
  непереводимы и `l10n:check` их не видит).
- **Тесты, которые проверяют сами себя.** Названный класс отказа в этом репозитории. В диффе есть
  тесты манифест-контракта и тип-левел проверка совместимости `ActionSpec`/`RawActionSpec`. Для
  каждого спросите: сравнивает ли он два независимых источника, или один порождён другим.
