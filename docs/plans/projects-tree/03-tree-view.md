# Этап 03. TreeView, декорации, размещение, локализация

Ревизия 3 после round 02: ключ идентичности узла — `rootId` + путь; `badge` получил жёсткое
ограничение (прежняя ревизия опиралась на ложный факт «лимита нет»); `highlights` перестал
называться основным носителем выделения; названы условия, при которых декорации не видны.

Цель: дерево видно в редакторе, важные узлы визуально выделены, размещение переключается настройкой,
интерфейс на двух языках.

## Пакет 03-A. TreeDataProvider и реестр узлов

Файлы: `src/editor/tree-view/{provider.ts,item.ts,registry.ts,index.ts}`, вклады `views` и
`viewsContainers` в `package.json`, `media/activity-icon.svg`.

```ts
type NodeKey = string                // `${rootId}:${pathFromRoot}` — не путь: корни могут перекрываться

class NodeRegistry {
  canonical(node: ClassifiedNode): ClassifiedNode   // существующий объект, обновлённый на месте
  forget(key: NodeKey): void
  invalidate(reason: 'rulesChanged' | 'rootsChanged'): void   // сбрасывает реестр целиком
}

class ProjectsTreeProvider implements vscode.TreeDataProvider<ClassifiedNode> {
  getChildren(element?: ClassifiedNode): Promise<ClassifiedNode[]>
  getTreeItem(element: ClassifiedNode): vscode.TreeItem
  refresh(node?: ClassifiedNode): void
}
```

Решения:
- **элементы не пересоздаются.** `ExtHostTreeView` держит `Map<T, TreeNode>` и адресует элементы по
  идентичности объекта (факт 4), поэтому `refresh` на новом экземпляре — молчаливый no-op без
  исключения. `NodeRegistry` выдаёт канонический объект на путь и обновляет его содержимое на месте.
  В первом релизе узлы и так живут долго, но контракт вводится сразу: этап 07 (фоновая
  перепроверка) без него сломался бы незаметно;
- `TreeItem.resourceUri` задаётся всегда — без него `FileDecorationProvider` не вызывается (факт 8);
- `contextValue` собирается из полей вердикта (`project`, `folder`, `root`) и `tags`;
- `TreeItem.id` стабилен и равен `NodeKey`, а не пути: два перекрывающихся корня иначе дают
  элементы с одинаковым id, и состояние раскрытия одного протекает в другой;
- **реестр сбрасывается при смене правил или корней.** Он живёт всю сессию, поэтому без явной
  инвалидации это кэш без инвалидации — тот самый класс, который вынесен в этап 07;
- сортировка: вес из `HighlightSpec.sortWeight`, затем папки/проекты, затем имя через
  `localeCompare` с числовой коллацией (`project2` перед `project10`).

Граничные случаи: корней ноль (welcome-экран, этап 05); корень стал недоступен в рантайме; узел
удалён с диска при раскрытии; очень широкий каталог — `getChildren` не строит дерево целиком.

DoD: дерево показывает тестовое дерево каталогов; сворачивание сохраняется; удаление папки на диске
не роняет расширение; интеграционный тест «`refresh` после подмены данных узла перерисовал ветку»
проходит (тест-страховка контракта идентичности).

## Пакет 03-B. Выделение узлов

Файлы: `src/editor/decorations/{labelHighlight.ts,decorationProvider.ts}`.

Два носителя, и **ни один не безусловен** — это признаётся прямо, а не сглаживается:

1. **`TreeItemLabel.highlights`** (факт 1) — стабильный API, диапазоны метки рендерятся отдельным
   стилем, локально для дерева. Цена в другом, чем считала прошлая ревизия: канал `matches` общий с
   подсветкой встроенного поиска (факт 3), поэтому страдает **поиск** — при фильтрации дерева
   пользователь не увидит подсветку совпадения на уже выделенных узлах. Включается
   `HighlightSpec.labelHighlight`.
2. **`FileDecorationProvider`** — цвет метки и бейдж. Провайдер глобален (факт 8): декорации
   появятся и в Explorer, бейдж конкурирует с git. Кроме того, пользователь может выключить
   декорации настройками `explorer.decorations.colors`/`.badges` — тогда этот носитель не работает
   вовсе. Применяется только к узлам с явно заданным `color`/`badge`.

Настоящий bold закрыт proposed API (факт 2) и не используется. Вывод для онбординга: выделение
объясняется как «подсветка метки, цвет и бейдж», с оговоркой, что цвет и бейдж пользователь может
выключить настройками Explorer.

- `propagate` распространяет декорацию **к предкам**, не к содержимому (факт 9). Включается
  осознанно — чтобы папка домена показывала наличие выделенных проектов внутри; при включении
  требуется явно сигналить `onDidChangeFileDecorations` для предков;
- вклад `contributes.colors` с собственными id, чтобы выделение читалось в светлой и тёмной теме и
  настраивалось через `workbench.colorCustomizations`;
- `badge` — **не более двух символов, это жёсткое ограничение API** (факт 7): при нарушении
  `FileDecoration.validate` бросает исключение и декорация отбрасывается целиком, унося с собой
  цвет. Валидация правил (02-B) отвергает более длинный бейдж, а адаптер никогда не создаёт
  декорацию без `color`, `badge` и `tooltip` — пустая декорация тоже запрещена.

DoD: правило `{ when: { kind: 'depth', max: 1 }, then: { highlight: … } }` выделяет первый уровень;
проверено в светлой и тёмной теме; узлы без `color`/`badge` не получают декораций в Explorer;
бейдж из трёх символов отвергается валидацией и не доходит до API; при выключенных
`explorer.decorations.*` дерево остаётся читаемым.

## Пакет 03-C. Размещение

Файлы: `package.json` (два объявления view с разными id + `when`), `src/editor/tree-view/location.ts`,
`src/editor/contextKeys.ts`.

Три режима настройки `projectsTree.location`:
- `activityBar` — свой контейнер с иконкой (дефолт);
- `explorer` — view внутри Explorer, менее инвазивно;
- `none` — дерева нет, только команда быстрого выбора проекта (этап 04).

**`when` смотрит на собственный булев context key, а не на настройку напрямую.** Расширение ставит
`projectsTree.locationIsActivityBar` / `.locationIsExplorer` через `setContext` при активации и при
смене настройки. Причина — факт 6: `config.` в `when` документирован для настроек, вычисляемых в
boolean, а `location` строковая; форма `config.projectsTree.location == 'activityBar'` прямой
цитатой не подтверждается, тогда как `setContext` документирован дословно. Прошлая ревизия висела
на непроверенном сочетании.

**Цена приёма, названная явно** (факт 5): id view уникален глобально, поэтому это два разных view, а
не одно в двух местах. Следствия, которые обязан покрыть этот пакет:
- провайдер регистрируется на оба id;
- `viewsWelcome` (этап 05) и `when` в `menus` (этап 04) дублируются на оба id;
- `activationEvents` перечисляют оба `onView:<id>`;
- состояние раскрытия у двух view раздельное. Решение: собственное хранение свёрнутых путей в
  глобальном состоянии, чтобы переключение размещения не теряло разложенное дерево;
- поведение контейнера в activity bar, когда его единственный view скрыт условием, проверяется
  вручную.

DoD: все три режима работают; переключение не требует Reload Window; разложенное дерево сохраняется
при переключении; контейнер не остаётся пустой иконкой в режимах `explorer`/`none`; context keys
выставлены при активации, а не только по событию смены настройки (иначе первый запуск даёт пустое
дерево).

## Пакет 03-D. Локализация

Файлы: `package.nls.json`, `package.nls.ru.json`, `l10n/bundle.l10n.json`,
`l10n/bundle.l10n.ru.json`, поле `l10n` в `package.json`.

- строки из `package.json` (команды, настройки, view) — через `%key%` и `package.nls*.json`;
- строки из кода — через `vscode.l10n.t()`; требуется **поле `l10n` в манифесте**, указывающее
  каталог бандлов (факт 19). Без него рантайм-локализация не работает вовсе;
- ключ в `l10n.t()` — сам английский текст, а не идентификатор: базовый бандл генерируется из кода,
  а не пишется руками;
- проверка полноты перевода добавляется в `pnpm check`: ключ, существующий в базовом бандле и
  отсутствующий в русском, — ошибка.

DoD: при установленном русском Language Pack интерфейс русский, включая строки из кода; скрипт
проверки ловит намеренно удалённый ключ перевода.

## Тестовый план этапа

Unit (vitest): сортировка узлов; сборка `contextValue`; отображение `HighlightSpec` в
`TreeItemLabel.highlights` и `FileDecoration`, включая отказ создавать пустую декорацию; полнота
локализации; `NodeRegistry` возвращает тот же объект на тот же `NodeKey` и различает одинаковые
пути в разных корнях; `invalidate` сбрасывает реестр.
Интеграционные (`@vscode/test-cli`, отдельная джоба CI): регистрация обоих view; `getChildren` на
временном дереве каталогов; `refresh` после обновления данных узла перерисовывает ветку;
переключение размещения; отсутствие исключений при удалении папки во время раскрытия.
Ручные: внешний вид выделения в светлой и тёмной теме; отсутствие протечки декораций в Explorer.
