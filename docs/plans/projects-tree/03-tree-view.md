# Этап 03. TreeView, декорации, размещение, локализация

Ревизия 3 после round 02: ключ идентичности узла — `rootId` + путь; `badge` получил жёсткое
ограничение (прежняя ревизия опиралась на ложный факт «лимита нет»); `highlights` перестал
называться основным носителем выделения; названы условия, при которых декорации не видны.

Цель: дерево видно в редакторе, важные узлы визуально выделены, размещение переключается настройкой,
интерфейс на двух языках.

## Пакет 03-A. TreeDataProvider и реестр узлов

Файлы: `src/editor/tree-view/{provider.ts,item.ts,registry.ts,index.ts}`, вклады `views` и
`viewsContainers` в `package.json`, `media/activity-icon.svg`.

```ts
type NodeKey = string                // `${rootId}:${pathFromRoot}` — не путь: корни могут перекрываться

class NodeRegistry {
  canonical(node: ClassifiedNode): ClassifiedNode   // существующий объект, обновлённый на месте
  forget(key: NodeKey): void
  invalidate(reason: 'rulesChanged' | 'rootsChanged'): void   // сбрасывает реестр целиком
}

class ProjectsTreeProvider implements vscode.TreeDataProvider<ClassifiedNode> {
  getChildren(element?: ClassifiedNode): Promise<ClassifiedNode[]>
  getTreeItem(element: ClassifiedNode): vscode.TreeItem
  refresh(node?: ClassifiedNode): void
}
```

Решения:
- **элементы не пересоздаются.** `ExtHostTreeView` держит `Map<T, TreeNode>` и адресует элементы по
  идентичности объекта (факт 4), поэтому `refresh` на новом экземпляре — молчаливый no-op без
  исключения. `NodeRegistry` выдаёт канонический объект на путь и обновляет его содержимое на месте.
  В первом релизе узлы и так живут долго, но контракт вводится сразу: этап 07 (фоновая
  перепроверка) без него сломался бы незаметно;
- `TreeItem.resourceUri` задаётся всегда — без него `FileDecorationProvider` не вызывается (факт 8);
- `contextValue` собирается из полей вердикта (`project`, `folder`, `root`) и `tags`;
- `TreeItem.id` стабилен и равен `NodeKey`, а не пути: два перекрывающихся корня иначе дают
  элементы с одинаковым id, и состояние раскрытия одного протекает в другой;
- **реестр сбрасывается при смене правил или корней.** Он живёт всю сессию, поэтому без явной
  инвалидации это кэш без инвалидации — тот самый класс, который вынесен в этап 07;
- сортировка: вес из `HighlightSpec.sortWeight`, затем папки/проекты, затем имя через
  `localeCompare` с числовой коллацией (`project2` перед `project10`).

Граничные случаи: корней ноль (welcome-экран, этап 05); корень стал недоступен в рантайме; узел
удалён с диска при раскрытии; очень широкий каталог — `getChildren` не строит дерево целиком.

DoD: дерево показывает тестовое дерево каталогов; сворачивание сохраняется; удаление папки на диске
не роняет расширение; интеграционный тест «`refresh` после подмены данных узла перерисовал ветку»
проходит (тест-страховка контракта идентичности).

## Пакет 03-B. Выделение узлов

Файлы: `src/editor/decorations/{labelHighlight.ts,decorationProvider.ts}`.

Два носителя, и **ни один не безусловен** — это признаётся прямо, а не сглаживается:

1. **`TreeItemLabel.highlights`** (факт 1) — стабильный API, диапазоны метки рендерятся отдельным
   стилем, локально для дерева. Цена в другом, чем считала прошлая ревизия: канал `matches` общий с
   подсветкой встроенного поиска (факт 3), поэтому страдает **поиск** — при фильтрации дерева
   пользователь не увидит подсветку совпадения на уже выделенных узлах. Включается
   `HighlightSpec.labelHighlight`.
2. **`FileDecorationProvider`** — цвет метки и бейдж. Провайдер глобален (факт 8): декорации
   появятся и в Explorer, бейдж конкурирует с git. Кроме того, пользователь может выключить
   декорации настройками `explorer.decorations.colors`/`.badges` — тогда этот носитель не работает
   вовсе. Применяется только к узлам с явно заданным `color`/`badge`.

Настоящий bold закрыт proposed API (факт 2) и не используется. Вывод для онбординга: выделение
объясняется как «подсветка метки, цвет и бейдж», с оговоркой, что цвет и бейдж пользователь может
выключить настройками Explorer.

- `propagate` распространяет декорацию **к предкам**, не к содержимому (факт 9). Включается
  осознанно — чтобы папка домена показывала наличие выделенных проектов внутри; при включении
  требуется явно сигналить `onDidChangeFileDecorations` для предков;
- вклад `contributes.colors` с собственными id, чтобы выделение читалось в светлой и тёмной теме и
  настраивалось через `workbench.colorCustomizations`;
- `badge` — **не более двух символов, это жёсткое ограничение API** (факт 7): при нарушении
  `FileDecoration.validate` бросает исключение и декорация отбрасывается целиком, унося с собой
  цвет. Валидация правил (02-B) отвергает более длинный бейдж, а адаптер никогда не создаёт
  декорацию без `color`, `badge` и `tooltip` — пустая декорация тоже запрещена.

DoD: правило `{ when: { kind: 'depth', max: 1 }, then: { highlight: … } }` выделяет первый уровень;
проверено в светлой и тёмной теме; узлы без `color`/`badge` не получают декораций в Explorer;
бейдж из трёх символов отвергается валидацией и не доходит до API; при выключенных
`explorer.decorations.*` дерево остаётся читаемым.

## Пакет 03-C. Размещение

Файлы: `package.json` (два объявления view с разными id + `when`), `src/editor/tree-view/location.ts`,
`src/editor/contextKeys.ts`.

Три режима настройки `projectsTree.location`:
- `activityBar` — свой контейнер с иконкой (дефолт);
- `explorer` — view внутри Explorer, менее инвазивно;
- `none` — дерева нет, только команда быстрого выбора проекта (этап 04).

**`when` смотрит на собственный булев context key, а не на настройку напрямую.** Расширение ставит
`projectsTree.locationIsActivityBar` / `.locationIsExplorer` через `setContext` при активации и при
смене настройки. Причина — факт 6: `config.` в `when` документирован для настроек, вычисляемых в
boolean, а `location` строковая; форма `config.projectsTree.location == 'activityBar'` прямой
цитатой не подтверждается, тогда как `setContext` документирован дословно. Прошлая ревизия висела
на непроверенном сочетании.

**Цена приёма, названная явно** (факт 5): id view уникален глобально, поэтому это два разных view, а
не одно в двух местах. Следствия, которые обязан покрыть этот пакет:
- провайдер регистрируется на оба id;
- `viewsWelcome` (этап 05) и `when` в `menus` (этап 04) дублируются на оба id;
- `activationEvents` перечисляют оба `onView:<id>`;
- состояние раскрытия у двух view раздельное. Решение: собственное хранение свёрнутых путей в
  глобальном состоянии, чтобы переключение размещения не теряло разложенное дерево;
- поведение контейнера в activity bar, когда его единственный view скрыт условием, проверяется
  вручную.

DoD: все три режима работают; переключение не требует Reload Window; разложенное дерево сохраняется
при переключении; контейнер не остаётся пустой иконкой в режимах `explorer`/`none`; context keys
выставлены при активации, а не только по событию смены настройки (иначе первый запуск даёт пустое
дерево).

## Пакет 03-D. Локализация

Файлы: `package.nls.json`, `package.nls.ru.json`, `l10n/bundle.l10n.json`,
`l10n/bundle.l10n.ru.json`, поле `l10n` в `package.json`.

- строки из `package.json` (команды, настройки, view) — через `%key%` и `package.nls*.json`;
- строки из кода — через `vscode.l10n.t()`; требуется **поле `l10n` в манифесте**, указывающее
  каталог бандлов (факт 19). Без него рантайм-локализация не работает вовсе;
- ключ в `l10n.t()` — сам английский текст, а не идентификатор: базовый бандл генерируется из кода,
  а не пишется руками;
- проверка полноты перевода добавляется в `pnpm check`: ключ, существующий в базовом бандле и
  отсутствующий в русском, — ошибка.

DoD: при установленном русском Language Pack интерфейс русский, включая строки из кода; скрипт
проверки ловит намеренно удалённый ключ перевода.

## Тестовый план этапа

Unit (vitest): сортировка узлов; сборка `contextValue`; отображение `HighlightSpec` в
`TreeItemLabel.highlights` и `FileDecoration`, включая отказ создавать пустую декорацию; полнота
локализации; `NodeRegistry` возвращает тот же объект на тот же `NodeKey` и различает одинаковые
пути в разных корнях; `invalidate` сбрасывает реестр.
Интеграционные (`@vscode/test-cli`, отдельная джоба CI): регистрация обоих view; `getChildren` на
временном дереве каталогов; `refresh` после обновления данных узла перерисовывает ветку;
переключение размещения; отсутствие исключений при удалении папки во время раскрытия.
Ручные: внешний вид выделения в светлой и тёмной теме; отсутствие протечки декораций в Explorer.

## Решения, изменённые при реализации

Записано по факту исполнения, а не задним числом под уже написанный код: каждый пункт — решение,
которое изменилось из-за проверенного факта или обнаруженного ограничения.

**Пустая иконка контейнера — проблемы нет.** 03-C требовал проверить вручную «поведение контейнера в
activity bar, когда его единственный view скрыт условием». Факт 47 опровергает посылку:
`hideIfEmpty: true` зашит безусловно для всех контейнеров расширений, а видимость пересчитывается на
любое изменение контекста. Иконка гаснет вместе со view. Ручной проверки и обхода не требуется.

**Хранилище раскрытия нужно по другой причине, чем считал план.** 03-C обосновывал собственное
хранение свёрнутых путей тем, что «состояние раскрытия у двух view раздельное». Факт 41 уточняет
картину: внутри одного view платформа сохраняет раскрытие сама (`PreserveOrCollapsed` /
`PreserveOrExpanded`), и `collapsibleState` из `getTreeItem` — лишь дефолт для узла, впервые
появившегося в этом view. Хранилище (`tree-view/expansion.ts`) поэтому не удерживает состояние
между обновлениями — это делает платформа, — а только переносит его между двумя id. Предикат
`isExpanded` умеет лишь поднять дефолт до `Expanded` и никогда не опускает до `Collapsed`: хранилище
хранит множество раскрытых ключей и не отличает «не трогали» от «свернули намеренно».

**Провайдер регистрируется на оба id всегда, а не по режиму.** План говорил «провайдер
регистрируется на оба id», не уточняя когда. Выбрана безусловная регистрация при активации:
видимость решает `when`, поэтому смена настройки не требует ни перерегистрации, ни Reload Window.
Отвергнута регистрация по режиму — она превращает каждое изменение настройки в работу с
disposable-ами, то есть в шов, а именно на непроверенных швах между пакетами погорел round 05 (M1).

**`propagate` выключен, и это решение пользователя после ревью.** Первая реализация ставила
`propagate = true` на каждую декорацию, читая план буквально («чтобы папка домена показывала наличие
выделенных проектов внутри»). Ревью round 06 (codex-11) и собственный флаг исполнителя сошлись на
том, что это превращает локальное выделение в глобальную политику: провайдер декораций глобален
(факт 8), поэтому бейдж, запрошенный на одном проекте, появляется и на папках над ним в Explorer —
там, где про ProjectsTree никто не просил, и где пользователь не может это выключить, не выключив
декорации целиком.

Решение: в первом релизе не распространять. Вместе с флагом снято и сигналирование предков через
`onDidChangeFileDecorations` — оно существовало только ради пропагации, а сигнал для декорации,
которая не распространяется, это работа без наблюдаемого эффекта, потерю которой не поймал бы ни один
тест. Обе половины возвращаются вместе, когда `propagate` станет полем правила: это правка
`HighlightSpec`, схемы файла правил и её валидации, то есть предмет этапа 04. Тест на «сигналим
только изменившийся узел» держит парность явно — включить флаг, не вернув сигнал, значит по факту 9
получить бейдж, который молча не появится.

**Отвергнуто:** оставить как было (не описывается честно в онбординге — насколько высоко всплывает
в Explorer, живым прогоном не проверено) и сразу заводить поле правила (открывает контракт файла
правил в этапе, который его не вводит).

**`ThemeColor` на планке 1.85 непрозрачен.** Факт 43 в исходной редакции объявлял `ThemeColor.id`
доступным на 1.85; это неверно, класс объявляет только конструктор (строка исправлена, запись
добавлена в таблицу опровергнутых). Следствие для 03-B: id цвета живёт в коде как обычная строка,
`ThemeColor` конструируется на самом краю и никогда не читается обратно — ни в production, ни в
тесте.

**Интеграционный тест размещения слабее, чем звучит DoD.** «Все три режима работают» проверяется на
двух уровнях, и ни один не проверяет всё: юнит-тест `manifest-contract.test.ts` сверяет манифест с
кодом (каждый view объявлен, каждый `when` смотрит на ключ, который код действительно ставит,
каждый режим показывает ровно один view), а интеграционный тест подтверждает лишь, что переключение
проходит без исключения и без перезагрузки окна. Прочитать фактическое значение context key из
extension host нечем — документированного API нет, и факта под это в `api-facts.md` не появилось.
Пересчёт `when` самой платформой остаётся непокрытым автоматически.

**`--user-data-dir` вынесен из репозитория.** Редактор открывает Unix-сокет внутри
`--user-data-dir`, а ядро ограничивает путь 103 символами; дефолт (`.vscode-test/user-data/` внутри
пакета) превышает лимит при любой реальной глубине checkout, и редактор падает на старте с
`listen EINVAL` до первого теста. `.vscode-test.mjs` задаёт короткий путь вне репозитория.

## Решения, изменённые по итогам ревью round 06

**Правила пользователя ложатся ПОВЕРХ дефолтных, а не вместо них.** Первая реализация подставляла
файл вместо `DEFAULT_RULES`. Прогон на реальном дереве показал цену: файл с одним правилом
`highlight` уносил с собой `repo-marker`, поэтому проектов не оставалось вовсе, обход не
останавливался, и дерево превращалось из 181 узла в 1865 — плоский список каталогов там, где
пользователь попросил только цвет. 424 теста этого не показали. Названная цена нового порядка:
дефолт нельзя удалить, только переопределить — что выразимо, потому что вердикт разрешается
first-match по полю.

**Правила читаются через поставщик, а не захватываются при создании провайдера.** Провайдер
получает `() => readonly Rule[]`, симметрично `listRoots`. Иначе правка файла требовала бы
перезагрузки окна или пересоздания провайдера; отвергнуты оба варианта — асинхронный `activate`
(утверждения об API под это в таблице нет) и disposal-хореография при каждой смене настройки. При
смене правил оба реестра идентичности сбрасываются: вердикт каждого узла мог измениться.

**Слежения за файлом правил нет.** Правка подхватывается на следующем refresh (кнопка, смена
настройки, открытие окна), а не мгновенно. Watcher — предмет
[07-cache-and-reactivity.md](07-cache-and-reactivity.md), факт 14 подтверждает его реализуемость.

**Состояние раскрытия хранится трёхзначно.** `expanded` / `collapsed` / нет мнения, вместо множества
раскрытых ключей. Множество не умело выразить «свёрнуто» для root-группы, у которой дефолт —
`Expanded`, поэтому свёрнутая группа открывалась заново в другом размещении. Старая форма
(массив ключей) читается по-прежнему и деградирует в `expanded`.

**`refresh()` упорядочен поколениями.** Два наложившихся обхода больше не могут установить
устаревшее дерево: каждый вызов отменяет предыдущий источник отмены и открывает новое поколение,
а результат применяется только если его поколение всё ещё текущее. Использован `GenerationTracker`
из этапа 02, а не новый примитив.

**Декорации при перекрывающихся корнях: первый победил.** `provideFileDecoration` получает только
`Uri` (факт 8), поэтому декорация на узел там невыразима в принципе. Порядок обхода (порядок корней
в настройке) определяет, чья декорация применится; остальные не применяются. Отвергнуто слияние
`HighlightSpec` по полям — «какой корень главнее» не имеет непроизвольного ответа, а молчаливое
слияние выглядело бы как настоящая декорация на узел.

**Живые тесты идут на планке 1.85, а не на latest stable.** Иначе единственная поверхность,
способная поймать нарушение планки, проверяла бы совсем другую версию. Локально переключается
`VSCODE_TEST_VERSION`; в CI матрицы нет — вторая версия стоит второй загрузки редактора.

**Что осталось непокрытым автоматически, названо прямо.** Пересчёт `when` самой платформой; факт
регистрации `createTreeView` для обоих id (конкурирующая регистрация на занятый id не бросает и не
сообщает о существующей — проверено на 1.85 и 1.136); регистрация `FileDecorationProvider` и
подписки на события раскрытия — ссылок на эти экземпляры наружу нет. Плюс замкнутый круг активации
(факт 57) остался непроверенным живым прогоном: `onStartupFinished` добавлен по стоимости ошибки.

**Хвостовой разделитель в пути корня срезается, симлинк и регистр — нет.** Дедупликация корней
(claude-01) шла по точному совпадению строки, поэтому `/a/b` и `/a/b/` оставались двумя корнями, и
пользователь видел одно поддерево дважды под двумя группами. Срезание происходит в разборе записи, а
не в дедупликации: результат становится `id` корня, а на `id` ключуется `NodeKey` и всё состояние на
узел. Путь, состоящий из одного разделителя (`/`), сохраняется — он и есть разделитель.

Симлинк и регистр на регистронезависимой ФС остаются непокрытыми **сознательно**: разрешение любого
из них требует обращения к ФС из синхронного чтения настроек и перезаписывает `id` каждого
существующего корня — то есть обнуляет сохранённое раскрытие у пользователей, у которых дубликатов
нет вовсе. Настоящий ответ даёт `identity()` из `discovery/file-system.ts`, и его место — этап 07,
который это состояние всё равно трогает. Ограничение закреплено тестом, чтобы оставалось решением,
а не недосмотром.
